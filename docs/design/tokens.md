# トークン設計

トークンはすべて短命にし、リフレッシュトークンは発行しない。アプリは IdP のセッションを使ったリダイレクトで、新しいトークンを取り直す。盗まれても長く使えるトークンを作らないための、Secure by Default の中心となる決定。

| 種類 | 形式 | 主な中身 | 有効期限 |
| --- | --- | --- | --- |
| ID トークン | JWT（`typ: JWT`、client に登録したアルゴリズム。既定は `Ed25519`） | 常に `iss`、`sub`、`aud`（client\_id）、`exp`、`iat`、`auth_time`、`nonce`（要求時）。スコープに応じて `name`（profile） | 5 分 |
| アクセストークン | JWT（`typ: at+jwt`、常に `Ed25519`） | `iss`、`sub`、`aud`（issuer）、`client_id`、`scope`、`exp`、`iat`、`jti` | 5 分 |
| 認可コード | 不透明な値（ハッシュ保存） | client、redirect\_uri、PKCE、nonce、発行の根拠になったセッションに紐付け | 60 秒 |
| セッション | `__Host-` Cookie（ハッシュ保存） | ユーザー、サインインに使ったパスキー（credential ID）、`auth_time` | サインインから 1 時間（絶対期限。延長しない） |
| 登録リンクのトークン | 256 bit の乱数をフラグメントに入れる（ハッシュ保存） | ユーザー | 発行から 10 分。1 回だけ使える |
| リフレッシュトークン | 発行しない | — | — |

この表と下の「クレームの一覧」が、発行するクレームの唯一の一覧になる。共有コアのテストは、[契約](cross-language-contract.md)のテストベクタでこの一覧と照らし合わせる。

- ID トークンとアクセストークンの有効期限は、どちらも 5 分にする。仕様は値を定めていないので、短いほうを選ぶ。ネイティブアプリ・CLI の再認証が増えることは許容する（[クライアントの種類](clients.md)参照）。
- セッションはサインインから 1 時間の絶対期限にし、使っても延長しない（スライディングにしない）。そのため、セッションを使うたびに D1 へ書く必要がない。NIST SP 800-63B-4 の AAL2 は、全体の再認証タイムアウトを設けなければならず（SHALL）24 時間以内にすべき（SHOULD）とし、無操作のタイムアウトは 1 時間以内にすべき（SHOULD）としている。固定の 1 時間はどちらも満たす。同期型のパスキーも AAL2 で使える（Appendix B）。
- 1 時間を過ぎると、RP から新たにリダイレクトされたときに、もう一度パスキーでサインインする。RP 側のセッションは各 RP が管理し、IdP のセッションが切れても終わらない。
- 登録リンクは発行から 10 分で切れ、1 回だけ使える。根拠は[認証フロー](authentication.md)を参照。
- `sub` は不変のランダム ID（UUIDv4）で、メールアドレスは使わない。将来 ledger などの外部サービスと結合するときのキー（`iss` + `sub`）になる。
- アクセストークンの `aud` は issuer にする。RFC 9068 §3 では `resource` の指定がなければ既定のリソースを `aud` に入れ、v1 でアクセストークンを受け取るのは IdP の `/userinfo` だけなので、既定のリソースを issuer とする。IdP の中で issuer あてのアクセストークンを受け付けるのは `/userinfo` だけにする。
- 複数の client が同じ IdP を使っても、どの client 向けのトークンかは `client_id` クレームで表す。`/userinfo` はこれを使って、その client に対するアクセス可否を判定する。
- 将来 API（認可レベル 3）を足すときは、resource ごとに登録した URI を `aud` にし、issuer あてのトークンでは API を呼べないようにする。
- クレームは要求されたスコープの分だけ返し、ID トークンにも同じ範囲だけを入れる。独自のクレーム（グループなど）は v1 では発行しない。
- メールアドレスは持たない。IdP は連絡にも復旧にも識別にもメールアドレスを使わないので、残る用途は RP への受け渡しだけになる。そのために他人の個人情報を保管するより、メールアドレスを必要とする RP が本人から必要な分だけ集めるほうがよい。`email_verified` を誤って扱うことによるアカウント乗っ取りの経路も、持たなければ生じない。
- `email` スコープは扱わない。要求されてもエラーにはせず無視し、`email` と `email_verified` のクレームは返さない。認可サーバーは要求されたスコープを一部無視してよく、発行したスコープが要求と異なるときはトークンレスポンスに `scope` を含める（RFC 6749 §3.3、§5.1）。既定で `openid email profile` を要求する RP が多いので、エラーにすると、メールアドレスなしで動く RP までつながらなくなる。
- 課金やプランに関する情報はクレームに一切入れない。

**クレームの一覧**

一次資料で確かめた、発行するものと発行しないものの一覧。

- ID トークンのヘッダーは `typ`（`JWT`）、`alg`、`kid`。
- ID トークンには、常に `iss`、`sub`、`aud`、`exp`、`iat` を入れる（OIDC Core §2 で REQUIRED）。
- `auth_time` は常に入れる。§2 は、`max_age` の要求か Essential Claim として要求されたときに REQUIRED、それ以外は OPTIONAL としている（`max_age` のときに必ず入れることは §3.1.2.1 にもある）。要求の有無で形を変えないために、常に入れる。
- `nonce` は、認可リクエストにあったときに入れる（§2 で、あれば入れなければならない（MUST）。RP の確認は §3.1.3.7 の 11）。
- `name` は `profile` スコープのときに入れる（§5.4）。値がないクレームを返さないことはエラーではない（§5.3.2、§5.5.1）。
- `azp` は入れない（§2 で OPTIONAL。拡張を使わない実装は `azp` を使わないことが推奨されている）。
- `at_hash` は入れない（§3.1.3.6 で認可コードフローでは OPTIONAL。implicit と hybrid のフローは提供しない）。
- `acr` と `amr` は入れない（§2 で OPTIONAL）。RFC 8176 §2 の `amr` の値では、同期型と端末に固定のパスキーを 1 つの値で正しく表せない（`hwk` はハードウェアで守られた鍵の所持の証明で同期型には当てはまらず、`swk` はソフトウェアで守られた鍵の所持の証明で端末に固定の鍵を過小に表す）。値を BE / BS フラグで出し分けても、RP がそれで判断を変える予定はない。`claims` パラメータに対応しないので、`acr` を Essential として要求されることはない（§5.5.1.1 の場合は起きない）。`acr_values` は無視する。
- `sid` は入れない（Core のクレームではなく、`sid` を使う Front-Channel Logout と Back-Channel Logout は実装しない）。RP-Initiated Logout の `id_token_hint` が今のセッションのものかは、`sub` と `auth_time` をセッションと比べて確かめる（[認証フロー](authentication.md)の「RP からのログアウト」参照）。
- `preferred_username` は入れない。§5.1 は RP がこの値の一意性に頼ってはならない（MUST NOT）とし、§5.7 は `name` と `preferred_username` を一意な識別子に使ってはならない（MUST NOT）としている。RP は `sub` で利用者を識別する。
- `scope` のクレームは ID トークンに入れない。
- アクセストークンには、RFC 9068 §2.2 で REQUIRED の `iss`、`exp`、`aud`、`sub`、`client_id`、`iat`、`jti` を入れ、`scope` も入れる（§2.2.3 で、認可リクエストに `scope` があれば入れるべき（SHOULD））。ヘッダーの `typ` は `at+jwt`（§2.1）。
- `/userinfo` は、常に `sub` を返し（OIDC Core §5.3.2 で MUST）、`profile` スコープのときに `name` を返す。
- トークンレスポンスは、`access_token`、`token_type`（`Bearer`。RFC 6749 §5.1 で REQUIRED）、`expires_in`（300。§5.1 で RECOMMENDED）、`id_token`（OIDC Core §3.1.3.3 で MUST）、`scope` を返す。`scope` は常に返す（§5.1 は、要求と異なるときに REQUIRED とする。`email` を無視したときは要求と異なる）。

**署名アルゴリズム**

- 通常の運用では、トークンに Ed25519 で署名する。JWS の `alg` には RFC 9864 の完全指定の識別子 `Ed25519` を使う（RFC 9864 §2.2 で定義され、§4.1.1 で JWS のアルゴリズムの登録簿に登録された。署名は RFC 8032 §5.1 の Ed25519）。
- 多態の識別子 `EdDSA`（RFC 8037 §3.1）は、RFC 9864 §4.1.2 で Deprecated になった。§4.4 は、Deprecated の識別子よりも置き換えの仕組みを新しいデプロイで使うべき（SHOULD）としている。IdP は `EdDSA` を発行せず、受け付けもしない。
- Ed25519 の鍵の表現は RFC 8037 と同じで、`alg` だけが `EdDSA` ではなく `Ed25519` になる（RFC 9864 §5）。公開鍵は `kty: OKP`、`crv: Ed25519`、`x` で表す（RFC 8037 §2）。
- アクセストークンは、常に Ed25519 で署名する。受け取るのは IdP 自身の `/userinfo` だけなので、RP の都合でアルゴリズムを変える理由がない。`/userinfo` は `alg` が `Ed25519` のアクセストークンだけを受け付ける。
- ID トークンは、client ごとに登録したアルゴリズム（`clients.id_token_signed_response_alg`、`Ed25519` か `RS256`）で署名する。OIDC Dynamic Client Registration 1.0 §2 は、`id_token_signed_response_alg` を省略したときの既定を RS256 としている。既定値に頼った解釈の食い違いを起こさないよう、`client_create` は値を必ず明示して登録し、指定がなければ `Ed25519` にする。`RS256` は、ライブラリが Ed25519 を検証できない RP にだけ選ぶ（[管理 CLI と管理用の Worker](idpctl.md)参照）。
- `id_token_hint` は IdP 自身が発行した ID トークンなので、`Ed25519` と `RS256` の両方を検証できるようにする。検証には、そのとき設定されている鍵だけを使う。
- JWT の検証では、`alg` と鍵の種類を結び付ける。`Ed25519` は `kty: OKP` かつ `crv: Ed25519` の鍵とだけ、`RS256` は RSA の鍵とだけ組み合わせ、それ以外の組み合わせと、`EdDSA`、`none` を含むほかの `alg` はすべて拒否する。RFC 8725 §3.1 は、各鍵をちょうど 1 つのアルゴリズムで使い、暗号操作のときにそれを確かめなければならない（MUST）としている。検証の前に、ヘッダーの `kid` で鍵を選び、その鍵の種類に合わない `alg` は署名を確かめる前に拒否する。ヘッダーは `alg`、`kid`、`typ` のちょうど 3 つだけを受け付け、`jwk`、`jku`、`x5u`、`crit` などほかのメンバーを含むものは拒否する。IdP が発行するヘッダーはこの 3 つだけで、トークンの側から鍵や処理を選ばせる経路をなくすため。

**RS256（任意の機能）**

RS256 は、デプロイ時に有効にする任意の機能にする。有効かどうかは、デプロイの設定ファイルの `rs256_enabled`（`true` か `false`）だけが決め（唯一の正）、2 つの Worker は同じ値を環境変数 `RS256_ENABLED` で受け取る。既定のデプロイは `false` で、RSA の鍵を持たない。

- IdP の Worker は、`rs256_enabled` が `true` なら RSA の鍵の current を必須にし、なければ設定の誤りとしてすべてのリクエストを拒否する。`false` なら RSA の Secret が残っていても読まない。
- discovery の `id_token_signing_alg_values_supported`、JWKS、client の登録で受け付けるアルゴリズムは、この設定と、それに従って読んだ鍵から導く。既定は `["Ed25519"]`、RS256 を有効にすると `["Ed25519", "RS256"]` になる。署名できないアルゴリズムを載せることはない。
- RS256 を無効にしている間は、OIDC Discovery 1.0 §3（`id_token_signing_alg_values_supported` に RS256 を含めなければならない（MUST））と、OIDC Core 1.0 §15.1（OP は ID トークンの RS256 での署名をサポートしなければならない（MUST）。例外は、ID トークンを Token Endpoint からだけ返し、client に `none` だけを登録させる OP）から外れる。IdP は `none` を使わないので、§15.1 の例外にも当たらない。また、アクセストークンは常に `Ed25519` で署名するので、RFC 9068 §2.1（準拠する認可サーバーは RS256 をサポートする署名アルゴリズムに含めなければならない（MUST））からも外れる。アクセストークンを検証するのは IdP 自身の `/userinfo` だけで、外部のリソースサーバーとの相互運用の問題はない。これらは標準からの逸脱として[標準準拠](standards-compliance.md)に例外として記録する。OIDC Core §3.1.3.7 の 7（`alg` は既定の RS256 か、登録時に送った `id_token_signed_response_alg` であるべき（SHOULD））は、client ごとにアルゴリズムを必ず明示して登録することで満たす。理由は、RSA を必要とする RP がいない間は、秘密鍵の素材と攻撃面（RSA の署名の実装、鍵の保管とローテーション）を最小にするため。
- 適合性テスト（Basic OP と Config OP）は、RS256 を有効にしたデプロイで流し、全項目の合格を求める。
- **有効にする**：RSA の鍵をリポジトリの生成スクリプトで生成し、Worker Secret に登録する（下の「署名鍵の生成とバックアップ」と同じ規則。`false` の間は読まれない）。その後で `rs256_enabled` を `true` にしてデプロイする。管理用の Worker は、RS256 が無効な間は、client への `RS256` の登録を拒否する。
- **無効にする**：`RS256` を登録した client が 1 つもないときだけ許す。管理 API は `RS256` を登録している client を一覧できる（`clients_list`）。最後の client を `Ed25519` に変えてから、ID トークンの有効期限（5 分）が過ぎた後に `rs256_enabled` を `false` にしてデプロイし、RSA の Secret を外す。それまでに発行した RS256 の ID トークンを RP が検証できるようにするため。
- `RS256` を登録した client があるのに RSA の鍵がない場合、その client へのトークンの発行は失敗させる（fail-closed）。`/authorize` は client と `redirect_uri` を検証した後、サインインの前に `server_error` を返す（RFC 6749 §4.1.2.1）。`/token` も、認可コードを消費する前に同じ確認を行い、トークンを発行せずにエラーを返す。別のアルゴリズムで署名して代わりに返すことはしない。
- 管理用の Worker は署名鍵を持たず、IdP の Worker へのバインディングも持たない。RS256 が有効かどうかは `RS256_ENABLED` だけで判断し、値がないか `true` でなければ有効でないものとして扱う（fail-closed）。
- IdP の Worker の実際の状態が設定と食い違っていないことは、デプロイの後の確認が確かめる。公開の discovery の `id_token_signing_alg_values_supported` が、`rs256_enabled` が `true` のときだけ `RS256` を含まなければ、デプロイを失敗にする（[デプロイと設定](deployment.md)のデプロイのパイプライン）。

**署名鍵**

- Ed25519 の鍵を常に持ち、RSA の鍵は RS256 を有効にするときだけ持つ。どちらも JWK を Worker Secret に置き、インポートした鍵はモジュールスコープでキャッシュする。
- 鍵の種類ごとに、current の Secret を必ず持ち、previous の Secret は最初のローテーションの後から持つ。Secret は、RS256 が無効なら Ed25519 の 1 つか 2 つ、有効なら RSA の 1 つか 2 つを足した数になる（最初のデプロイは Ed25519 の current だけ）。JWKS には、設定されたすべての鍵の公開鍵を載せる。
- Ed25519 の current がない、RSA の previous だけがある、同じ鍵を 2 つの Secret に置いている、JWK の形が[契約](cross-language-contract.md)と合わないなど、鍵の設定が不正なら、リクエストを処理せずエラーを返す（fail-closed）。

**署名鍵のローテーション**

- 鍵の種類ごとに独立してローテーションする。Ed25519 の鍵を替えるときに RSA の鍵は替えず、その逆も同じ。
- 1 回の Worker のデプロイで、その種類の新しい鍵を current に、それまでの current を previous にする（それまでの previous は外す）。新しい公開鍵は、遅くともその鍵で署名する最初のトークンと同時に JWKS に載る。
- これで OIDC Core §10.1（署名に使う鍵は JWK Set に公開しなければならない）に準拠する。§10.1.1 は待機期間を定めず、見慣れない `kid` を見た検証側が JWKS を取り直すとしている。
- 次の鍵を前もって JWKS に載せておく（事前公開）ことはしない。見慣れない `kid` を見ても JWKS を取り直さない RP が見つかったときだけ、事前公開を検討し直す。

**署名鍵の生成とバックアップ**

- 鍵の形式（Ed25519 と RSA 4096 bit、`kid` は JWK thumbprint など）は [実装に依存しない契約](cross-language-contract.md)で固定する。
- 鍵は必ずリポジトリのレビュー済みの生成スクリプトで生成する。手で生成すると、手順のずれ（鍵の長さ、`kid` の計算、`alg` や `use` の付け忘れ、平文のファイルの置き忘れ）が鍵ごとに起き、それが最も危険なため。スクリプトを通せば、人が実行してもエージェント（AI）が実行しても結果は同じなので、実行する主体は限らない。`idpctl` も管理用の Worker も鍵を生成しない。管理者の秘密鍵（管理 API の要求に RFC 9421 の署名を付ける鍵。[管理 CLI と管理用の Worker](idpctl.md)参照）とは別の鍵である。
- スクリプトは、生成した秘密鍵を `op` で 1Password の Vault のアイテムに、パイプで Worker Secret に直接渡し、平文をディスクに書かない。`kid`（RFC 7638 の JWK thumbprint）はスクリプトが自分で計算する。出力するのは秘密でない値（`kid`、公開鍵）だけにする。Worker Secret は書き込み専用で読み出せないので、バックアップと正本は 1Password のアイテムとする（[デプロイと設定](deployment.md)参照）。
- 秘密鍵の値を AI のコンテキストに入れてはいけない。この規則は、誰がスクリプトを実行するかにかかわらず変わらない。
