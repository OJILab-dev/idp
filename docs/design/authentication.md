# 認証フロー

サインインは「client と redirect\_uri を最初に検証 → パスキーでセッションを作る → 使い捨ての認可コードをトークンに交換」の順で進む。どの段階でも、検証が終わる前の値は信用しない。

**サインイン（認可コードフロー）**

1. RP アプリが `/authorize` にリダイレクトする。Worker は最初に `client_id` と `redirect_uri`（完全一致。ループバックだけポートを問わない）を検証し、不一致ならリダイレクトせずエラーページを返す。続いて `scope` に `openid` が含まれるかを確認し、なければ検証済みの `redirect_uri` に `invalid_scope` を返す。`openid` がないときの動作は仕様で規定されていない（OIDC Core §3.1.2.1）ので、仕様の要求ではなく fail-closed（設計原則 4）の方針として拒否する。
2. `effective_access` で、セッションのユーザーがこのクライアントを使えるか確認する（セッションがなければ手順 4 へ。public client は、セッションがあっても `prompt=login` と同じに扱って手順 4 へ）。使えなければ、検証済みの `redirect_uri` に `access_denied` を返す。セッションの Cookie は SameSite=Lax なので、クロスサイトからの `POST /authorize` にはセッションが付かず、常に手順 4 のパスキーのサインインに進む。安全側に倒れる、意図した動作である。
3. アクセスが許可されていれば、認可コード（60 秒、ハッシュ保存）を発行して `redirect_uri` に戻す。`prompt=none` のとき、セッションがないか public client からの要求なら、検証済みの `redirect_uri` にだけ `login_required` を返す。
4. セッションがない、または `prompt=login` や `max_age` で再認証が必要なら、検証済みのリクエストを `authorize_requests` に保存し（15 分。そこから発行するチャレンジより先に切れないよう、10 分のセレモニーにページ読み込みの余裕を足す）、その ID を `__Host-` Cookie に入れて、静的アセットのサインインページを表示する。ページは `/webauthn/auth/options` でチャレンジ（256 bit、10 分、D1 に保存）を受け取り、ブラウザでパスキーの署名を作る。discoverable credential を使うのでこの時点ではユーザーが分からず、チャレンジは Cookie の認可リクエスト（`authorize_request_id_hash`）に紐付けて保存する。
5. `/webauthn/auth/verify` でユーザー検証（UV）必須、origin と RP ID 固定で署名を検証し、チャレンジが同じ Cookie の認可リクエストに紐付いていることを確認してから、チャレンジを原子的に消費する。成功したら古いセッションを破棄して新しいセッション（サインインから 1 時間の絶対期限で、延長しない）を作り、ページは `/authorize/resume` に移る。
6. `/authorize/resume` は Cookie の ID で `authorize_requests` の行を `DELETE … RETURNING` で一度だけ取り出し、Cookie を消す。行がない、または期限切れならエラーページを返す。client と `redirect_uri` が今も登録どおりか、アクセス可否、`prompt=login` または public client ならセッションの `auth_time` が行の `created_at` 以降か、`max_age` と `id_token_hint` の条件を確認し直してから、手順 3 と同じく認可コードを発行する。
7. RP アプリが `/token` を呼ぶ。クライアント認証（`client_secret_basic`。public client は認証せず `client_id` だけを送る）、PKCE、redirect\_uri、ユーザーの現在のアクセス可否をすべて検証してから、認可コードを原子的に消費し、ID トークンとアクセストークンを返す。
8. `/userinfo` は、`typ` が `at+jwt` で `aud` が issuer のアクセストークンだけを受け付ける。毎回 D1 からユーザーを読み直し、無効化されたユーザーと、トークンの `client_id` を使えなくなったユーザーは拒否する。

**認可エンドポイントのエラーの返し方**

- `client_id` と `redirect_uri` を検証できなかったときだけ、リダイレクトせずエラーページを返す（RFC 6749 §4.1.2.1）。
- 検証が済んだ後のエラーは、すべて検証済みの `redirect_uri` に `error`、`state`（リクエストにあった場合）、`iss` を付けて返す（RFC 6749 §4.1.2.1、OIDC Core §3.1.2.6、RFC 9207）。
- 成功時の認可レスポンスにも、リクエストにあった `state` をそのまま付ける（RFC 6749 §4.1.2）。

**パスキーの登録**

1. 管理者が `idpctl` でユーザーを作成し、登録リンク（`/enroll#<token>`。256 bit、発行から 10 分、1 回だけ使える）を発行する。リンクは本人に渡すその場で発行し、メールではなく、対面など信頼できる経路で渡す。トークンは URL のフラグメントに入れ、サーバーのログに残さない。
2. 登録ページはフラグメントからトークンを読み、`/webauthn/register/options` でチャレンジを受け取る。チャレンジは登録トークンに紐付けて保存する。
3. `/webauthn/register/verify` で、チャレンジとトークンの紐付けを確認してからトークンを消費し、パスキーを `credentials` に保存する。

登録リンクによる登録は、常にパスキーの追加として扱い、既存のパスキーには触れない。

**本人によるパスキーの追加**

1 人のユーザーに複数のパスキーを登録できる（NIST SP 800-63B-4 §4.1.2.1 は複数の認証器の結び付けを許可しなければならない（SHALL）とし、2 つ以上の手段を持つよう促すべき（SHOULD）としている）。2 本目以降は、サインイン中の本人が追加できる。

1. サインイン済みのページが `/webauthn/add/begin` を呼ぶ。Worker はセッションを確認し、そのユーザーのパスキーだけを `allowCredentials` に入れた認証用のチャレンジを、セッション（`session_token_hash`）に紐付けて発行する。
2. ブラウザが既存のパスキーで、ユーザー検証（UV）付きの署名を作る。`/webauthn/add/options` は、チャレンジが同じセッションに紐付いていること、署名したパスキーがセッションのユーザーのものであること、UV を確認してからチャレンジを消費し、登録用のチャレンジ（`excludeCredentials` にそのユーザーのパスキーを入れる）を同じセッションに紐付けて発行する。
3. `/webauthn/add/verify` は、登録用のチャレンジが同じセッションに紐付いていることを確認して消費し、パスキーを `credentials` に追加する。

- **追加の直前に再認証する**：セッションの Cookie だけでは追加できないようにする。§4.1.2.1 は、認証器を結び付けるときに、アカウントで使える最大の AAL で認証させなければならない（SHALL）としている。セッションを盗んだだけの攻撃者は、本人の認証器と UV を持たないので追加できない。再認証を突破できる攻撃者は、追加しなくてもすでに本人になりすませる。
- **本人は削除できない**：本人ができるのは追加だけで、失効は管理者が `passkey_revoke` で行う。攻撃者に本人のパスキーを消されて、本人が締め出されることを防ぐ。
- **本数の上限**：1 人あたり 10 本までにする。上限を超える追加は拒否する。
- **記録**：§4.1 は、結び付けた認証器と、そのライフサイクルの出来事の日時を記録しなければならない（SHALL）としている。`credentials` に作成日時と追加の経路（`enroll` か `self`）を持ち、管理者は `user_get` で一覧できる。結び付けは Worker が、失効は `idpctl` が監査ログに書き、管理者は `audit_tail` でいつでも確認できる（[データモデル](data-model.md)参照）。

**復旧**

全端末のパスキーを使えなくなったときの復旧は、管理者が発行する登録リンクだけで行う。本人がサインインできない以上、本人による追加は使えない。

1. 管理者が本人と対面で状況を確認し、新しい登録リンクを発行して渡す。
2. 本人が新しいパスキーを登録する（追加として扱われる）。
3. 管理者が `user_get` で一覧を見て、失くしたパスキーを `passkey_revoke` で 1 本ずつ失効させる。§4.2 の中で、侵害された認証器は速やかに停止、無効化、破棄しなければならない（SHALL）とされている。

§4.2 は復旧の方法として、保存型や発行型の復旧コード、復旧の連絡先、身元確認のやり直しのどれかを提供しなければならない（SHALL）としつつ、CSP の担当者とのやり取りのような独自の方法を、リスク分析に基づいて記録したうえで使ってよい（MAY）としている。この IdP は、管理者が本人を直接知っている家族規模の運用を前提に、対面での確認と登録リンクの受け渡しを独自の方法として使う。復旧コードは発行しない。

**NIST の通知要件の例外**

§4.1.2.1 は、認証器を追加したとき、追加とは独立した経路で本人に通知しなければならない（SHALL）としている。§4.6 は通知の宛先（メールアドレス、電話番号など）を 2 つ以上持たなければならない（SHALL）とし、§4.2 は復旧のときにも通知を求めている。この IdP は個人情報を持たない方針（[設計の概要](README.md)の設計原則 7）で通知の宛先を持たないので、これらの要件には従わない。例外として次のように補う。

- 本人による追加は、直前の再認証で予防する。通知は事後の検知の手段であり、通知が守る「セッションを盗まれて認証器を足される」脅威は、再認証で事前に防ぐ。
- 復旧は管理者と本人の対面で行うので、本人はその場で出来事を知っている。
- 本人への通知はしないが、パスキーの結び付けはすべて監査ログに残り、管理者はいつでも `audit_tail` と `user_get` で確認できる。再認証を突破した攻撃者が追加したパスキーに気付く手段は、管理者のこの確認だけであることを受け入れる。

**登録リンクの有効期限**

- 登録リンクは、管理者のもとで発行した値を本人の端末に持ち込み、パスキーを結び付けるためのものなので、NIST SP 800-63B-4 の「Binding Across Endpoints」の binding code の上限に合わせる。binding code は 1 回しか使えず（SHALL）、有効期間は最大 10 分で（SHALL）、メールのような安全でない経路で伝えてはならない（SHALL NOT）。
- 10 分は、パスキーを失くしたときの復旧として見た場合の、§4.2 の recovery code の上限のうち厳しいほう（SMS や音声で送るときの 10 分）にも収まる。
- トークンは 256 bit の乱数で、求められる強度を大きく上回る。

**サインアウト**

- 利用者は `POST /logout`（同一オリジン確認付き）で IdP のセッションを終了できる。セッション行を削除し、Cookie も消す。
- 管理者は `idpctl` の `session_revoke` で、ユーザーの全セッションを失効させられる。`user_disable` と `passkey_revoke` も、そのユーザーの既存セッションを削除する。
- RP-Initiated Logout などの OIDC のログアウト仕様は、v1 では実装しない。
