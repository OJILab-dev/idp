# 認証フロー

サインインは「client と redirect\_uri を最初に検証 → パスキーでセッションを作る → 使い捨ての認可コードをトークンに交換」の順で進む。どの段階でも、検証が終わる前の値は信用しない。

**サインイン（認可コードフロー）**

1. RP アプリが `/authorize` にリダイレクトする。Worker は最初に `client_id` と `redirect_uri`（完全一致。ループバックだけポートを問わない）を検証し、不一致ならリダイレクトせずエラーページを返す。client が無効（`client_enablement` が `enabled` でない、または行がない）なときも、`redirect_uri` が一致していてもリダイレクトせずエラーページを返す。無効にした RP の redirect URI は、もう信頼できないかもしれないため。続いて `scope` に `openid` が含まれるかを確認し、なければ検証済みの `redirect_uri` に `invalid_scope` を返す。`openid` がないときの動作は仕様で規定されていない（OIDC Core §3.1.2.1）ので、仕様の要求ではなく fail-closed（設計原則 4）の方針として拒否する。
2. `effective_access` で、セッションのユーザーがこのクライアントを使えるか確認する（セッションがなければ手順 4 へ。public client は、セッションがあっても `prompt=login` と同じに扱って手順 4 へ）。使えなければ、検証済みの `redirect_uri` に `access_denied` を返す。セッションの Cookie は SameSite=Lax なので、クロスサイトからの `POST /authorize` にはセッションが付かず、常に手順 4 のパスキーのサインインに進む。安全側に倒れる、意図した動作である。
3. アクセスが許可されていれば、認可コード（60 秒、ハッシュ保存）を、発行の根拠になったセッションに紐付けて発行し、`redirect_uri` に戻す。`prompt=none` のとき、セッションがないか public client からの要求なら、検証済みの `redirect_uri` にだけ `login_required` を返す。
4. セッションがない、または `prompt=login` や `max_age` で再認証が必要なら、検証済みのリクエストを `authorize_requests` に保存し（15 分。そこから発行するチャレンジより先に切れないよう、10 分のセレモニーにページ読み込みの余裕を足す）、その ID を `__Host-` Cookie に入れて、静的アセットのサインインページを表示する。行には、Worker が決めた UI の言語（下の「画面と言語」参照）も保存し、サインインページの URL のクエリ（`/signin?lang=<言語>`）で渡す。ページは読み込みのたびに `/webauthn/auth/options` でチャレンジ（256 bit、10 分、D1 に保存）を 1 つ受け取り、ブラウザでパスキーの署名を作る。discoverable credential を使うのでこの時点ではユーザーが分からず、チャレンジは Cookie の認可リクエスト（`authorize_request_id_hash`）に紐付けて保存する。
5. `/webauthn/auth/verify` でユーザー検証（UV）必須、origin と RP ID 固定で署名を検証し、チャレンジが同じ Cookie の認可リクエストに紐付いていることを確認してから、チャレンジを原子的に消費する。成功したら古いセッションを破棄して新しいセッション（サインインから 1 時間の絶対期限で、延長しない）を作り、ページは `/authorize/resume` に移る。セッションには、サインインに使ったパスキーの credential ID を記録する。セッションの根拠はそのパスキーにあるので、パスキーを失効させると、外部キーの連鎖でそのパスキーから作ったセッションも消える。
6. `/authorize/resume` は Cookie の ID で `authorize_requests` の行を `DELETE … RETURNING` で一度だけ取り出し、Cookie を消す。行がない、または期限切れならエラーページを返す。client と `redirect_uri` が今も登録どおりか、アクセス可否、`prompt=login` または public client ならセッションの `auth_time` が行の `created_at` 以降か、`max_age` と `id_token_hint` の条件を確認し直してから、手順 3 と同じく認可コードを発行する。
7. RP アプリが `/token` を呼ぶ。client が有効であること、クライアント認証（`client_secret_basic`。public client は認証せず `client_id` だけを送る）、PKCE、redirect\_uri、ユーザーの現在のアクセス可否、コードを発行したセッションが今も残っていて期限内であることをすべて検証してから、認可コードを原子的に消費し、ID トークンとアクセストークンを返す。
8. `/userinfo` は、`typ` が `at+jwt` で `aud` が issuer のアクセストークンだけを受け付ける。毎回 D1 からユーザーを読み直し、無効化されたユーザーと、トークンの `client_id` を使えなくなったユーザー（client やグループの無効化を含む。`effective_access` が除く）は拒否する。

無効な client からの `/token` は、クライアント認証の前に拒否し、`invalid_client` を返す（RFC 6749 §5.2）。認可コードは消費しない。認証の前に拒否すると、その client が無効であることだけは認証なしで分かるが、client identifier は秘密ではない（RFC 6749 §2.2）ので、これを受け入れる。シークレットの正しさや、ほかの状態は明かさない。

**無効化されたユーザー**

無効化されたユーザーは、どの経路でも新しい状態を作れないようにする。`user_disable` は既存のセッションを消すが、無効化の前に始めたセレモニーが後から完了する競合も、書き込みの側で止める。「無効化されていない」は、`user_enablement` の今の状態が `enabled` であることを指し、行のないユーザーは無効として扱う（[データモデル](data-model.md)参照）。

- `/webauthn/auth/verify` は、署名したパスキーのユーザーが無効化されていればセッションを作らない。セッションの挿入に「ユーザーが無効化されていない」条件を付け、確認と挿入の間に無効化されても作られないようにする。`/authorize/resume` と `/token` では `effective_access` が無効化されたユーザーを除くが、それに頼らず、セッション自体を作らない。
- 登録リンクによる登録は、`/webauthn/register/options` と `/webauthn/register/verify` の両方で、トークンのユーザーが無効化されていれば拒否する。verify ではパスキーの挿入に同じ条件を付ける。
- 本人による追加と失効は、begin、options、verify のすべてで、セッションのユーザーが無効化されていないことを確かめ直す。書き込み（追加の挿入、失効の削除）にも同じ条件を付ける。

**セッションと認可コードの関係**

セッションが終われば（期限切れ、サインアウト、`session_revoke`、パスキーの失効）、そのセッションから発行した未使用の認可コードも使えなくする。認可コードを `sessions` への外部キーで紐付けるので、セッションの行が消えればコードも連鎖で消える。行が残ったまま期限が切れた場合は連鎖では消えないので、`/token` でセッションの期限も確かめる。

これは仕様の要求ではない。RFC 6749 §4.1.2 が認可コードに求めるのは、発行後すぐに期限切れにすること（MUST）、最大 10 分を推奨すること、一度しか使えないこと、client identifier と redirection URI に紐付くことで、認可サーバーのセッションとの関係は定めていない。OIDC Core §3.1.3.2 も「Verify that the Authorization Code is valid.」と求めるだけで、何をもって有効とするかは認可サーバーに委ねている。ここでは「セッションが終われば、そこから新しいものは何も出ない」と言い切れるように、fail-closed（設計原則 4）の方針としてセッションが残っていることを有効の条件に含める。`/token` でアクセス可否を確かめ直すだけでは、失効したパスキーから作ったセッションのコードを止められない（ユーザーもアクセス権もそのまま残っているため）。

すでに発行した ID トークンとアクセストークン（5 分）は JWT なので取り消せず、期限まで有効なまま残る。RP 側のセッションは RP が管理するもので、IdP のセッションが終わっても続く（OIDC のログアウト仕様は v1 では実装しない）。

**認可エンドポイントのエラーの返し方**

- `client_id` と `redirect_uri` を検証できなかったときだけ、リダイレクトせずエラーページを返す（RFC 6749 §4.1.2.1）。
- 検証が済んだ後のエラーは、すべて検証済みの `redirect_uri` に `error`、`state`（リクエストにあった場合）、`iss` を付けて返す（RFC 6749 §4.1.2.1、OIDC Core §3.1.2.6、RFC 9207）。
- 成功時の認可レスポンスにも、リクエストにあった `state` をそのまま付ける（RFC 6749 §4.1.2）。

**パスキーの登録**

1. 管理者が `idpctl` でユーザーを作成し、登録リンク（`/enroll#<token>`。256 bit、発行から 10 分、1 回だけ使える）を発行する。リンクは本人に渡すその場で発行し、メールではなく、対面など信頼できる経路で渡す。トークンは URL のフラグメントに入れ、サーバーのログに残さない。
2. 登録ページはフラグメントからトークンを読み、`/webauthn/register/options` でチャレンジを受け取る。チャレンジは登録トークンに紐付けて保存する。
3. `/webauthn/register/verify` で、チャレンジとトークンの紐付けを確認してチャレンジを消費し、続けてトークンを消費し、パスキーを `credentials` に保存する。チャレンジは登録トークンへの外部キーを持ち、トークンを消すと連鎖で消えるので、消費は必ずチャレンジ、トークンの順にする。
4. verify が成功したのにブラウザが応答を受け取れなかった（通信が切れたなど）場合、トークンは消費済みで、パスキーは保存されている。登録ページは、もう一度登録するよう求めるのではなく、アプリからサインインを試すよう案内する。サインインできなければ、管理者に新しい登録リンクを頼む。

登録リンクを発行し直すと、同じバッチでそのユーザーの未使用の登録トークンがすべて消えるので、有効なリンクはユーザーごとに常に 1 つまでになる（[管理 CLI と管理用の Worker](idpctl.md)参照）。

登録リンクによる登録は、常にパスキーの追加として扱い、既存のパスキーには触れない。本人による追加と同じくパスキーの上限（下記）を適用し、すでに上限に達していれば保存しない。上限の確認は挿入と同じ文の条件で行い、同時に登録しても上限を超えない。`idpctl` も、上限に達しているユーザーや無効化されたユーザーには登録リンクを発行しない（本人の目の前ではなく、管理者の側で失敗させるため）。発行から使用までの間に本人が追加することもあるので、verify での確認は省かない。

**アカウントページ**

サインイン中の本人が自分のパスキーを扱うページとして、`/account` を置く。

- サインインページや登録ページと同じく純粋な静的アセットとし、`run_worker_first` の対象に含めない（[無料枠](free-tier.md)参照）。ページ自体はセッションを確かめず、データはすべて下の API から受け取る。
- ページでできるのは、自分のパスキーの一覧の表示、本人によるパスキーの追加と失効、`POST /logout` によるサインアウトだけにする。
- 一覧は `GET /webauthn/credentials` で受け取る。この API はセッションを確かめ、セッションのユーザーのパスキーだけを返す。返すのは credential ID、作成日時、最終使用日時、追加の経路（`enroll` か `self`）、同期型かどうか（backup state）だけで、公開鍵や sign count、ほかのユーザーの情報は返さない。ユーザーが無効化されていれば返さない。
- この API は GET でも状態を変える POST と同じく同一オリジンの確認を通ったリクエストだけを受け付け、`Sec-Fetch-Site` が `same-origin` でなければ拒否する（ヘッダーがないときも拒否する。同一オリジンの GET には `Origin` が付かないことがあり、代わりにできないため）。読み取りだけの API でも、Cookie が付くクロスサイトのトップレベルのナビゲーションでは返さないよう、fail-closed（設計原則 4）の方針として確認する。レスポンスには `Cache-Control: no-store` を付ける。
- v1 には、`/authorize` を経由しないサインインを置かない。サインインのチャレンジは常に `authorize_requests` に紐付けたままにし、サインインの経路を 1 つに保つ。セッションがないときは、API がエラーを返し、ページは「アプリからサインインしてから開き直す」よう案内する。セッションは 1 時間で切れるので、本人はアプリにサインインした後、その時間内にアカウントページを開く。
- 新しい API のパス（`/webauthn/credentials`、`/webauthn/add/*`、`/webauthn/revoke/*`）も、WAF のレート制限の対象（`/webauthn/*`）に含まれる（[無料枠](free-tier.md)参照）。

**本人によるパスキーの追加**

1 人のユーザーに複数のパスキーを登録できる（NIST SP 800-63B-4 §4.1.2.1 は複数の認証器の結び付けを許可しなければならない（SHALL）とし、2 つ以上の手段を持つよう促すべき（SHOULD）としている）。2 本目以降は、サインイン中の本人がアカウントページ（下記）から追加できる。

1. アカウントページが `/webauthn/add/begin` を呼ぶ。Worker はセッションを確認し、そのユーザーのパスキーだけを `allowCredentials` に入れた認証用のチャレンジを、セッション（`session_token_hash`）に紐付けて発行する。
2. ブラウザが既存のパスキーで、ユーザー検証（UV）付きの署名を作る。`/webauthn/add/options` は、チャレンジが同じセッションに紐付いていること、署名したパスキーがセッションのユーザーのものであること、UV を確認してからチャレンジを消費し、登録用のチャレンジ（`excludeCredentials` にそのユーザーのパスキーを入れる）を同じセッションに紐付けて発行する。
3. `/webauthn/add/verify` は、登録用のチャレンジが同じセッションに紐付いていることを確認して消費し、パスキーを `credentials` に追加する。挿入と監査ログの行には同じ条件（ユーザーが無効化されていない、パスキーの本数が上限未満）を付けて同じバッチに置き、挿入が起きたときだけ監査ログの行が残るようにする。

- **追加の直前に再認証する**：セッションの Cookie だけでは追加できないようにする。§4.1.2.1 は、認証器を結び付けるときに、アカウントで使える最大の AAL で認証させなければならない（SHALL）としている。セッションを盗んだだけの攻撃者は、本人の認証器と UV を持たないので追加できない。再認証を突破できる攻撃者は、追加しなくてもすでに本人になりすませる。
- **本数の上限**：1 人あたりのパスキーに上限を設ける。値は [実装に依存しない契約](cross-language-contract.md)の「パスキーの上限」で 1 か所だけに定め、仕様に根拠のない暫定の値として扱う。上限は本人による追加だけでなく、登録リンクによる登録を含むすべての結び付けの経路に適用し、上限を超える結び付けは拒否する。本数の確認は挿入と同じ文の条件で行い（失効の本数の確認を削除と同じ文で行うのと同じ）、同時に追加しても上限を超えない。

**本人によるパスキーの失効**

端末を失くしたり手放したりしたとき、本人がそのパスキーを止められる。追加と同じく、セッションだけでは進めない。

1. アカウントページが、失効させるパスキーの credential ID を付けて `/webauthn/revoke/begin` を呼ぶ。Worker はセッションを確認し、そのパスキーがセッションのユーザーのものであることを確かめてから、そのユーザーのパスキーだけを `allowCredentials` に入れた認証用のチャレンジを、セッションと失効させる credential ID の両方に紐付けて発行する。
2. ブラウザが既存のパスキーで UV 付きの署名を作る。`/webauthn/revoke/verify` は、チャレンジが同じセッションと同じ credential ID に紐付いていること、署名したパスキーがセッションのユーザーのものであること、UV を確認してからチャレンジを消費する。
3. 同じバッチで、そのユーザーのパスキーが 2 本以上ある場合に限って対象を削除し、監査ログに書く。本数の確認は削除と同じ文の条件で行い、同時に 2 本を失効させて 0 本になる競合を防ぐ。監査ログの行は、削除と同じ条件を付けた `INSERT … SELECT` を削除の直前の文に置いて書き、削除が実際に起きたときだけ残す。拒否されたときは成功の行を書かない（[データモデル](data-model.md)参照）。チャレンジは失効させるパスキーへの外部キーを持ち、パスキーを消すと連鎖で消えるので、消費はパスキーの削除より先に行う。
4. 外部キーの連鎖で、失効させたパスキーから作ったセッションが消え、そのセッションから発行した未使用の認可コードも消える。端末に縛られたパスキーならその端末のセッションだけが、同期型のパスキーなら同じ credential を使う全端末のセッションが消える。別のパスキーから作ったセッションは残る。今のセッションを作ったパスキーを失効させた場合は、今のセッションも消え、本人はサインアウトした状態になる（ページはその旨を表示する）。

- **最後の 1 本は失効できない**：パスキーが 1 本しかないときは拒否する。本人が自分を締め出す事故を防ぐ。失効させたいパスキーしかないなら、先に新しいパスキーを追加してから失効させる。
- **再認証に使ったパスキー自身も失効できる**：2 本以上あれば、残りでサインインできるので問題ない。そのパスキーが今のセッションを作ったものなら、上の連鎖で今のセッションも終わる。たとえば、手放す端末のパスキーをその端末で失効させると、その端末でのサインインもその場で終わる。
- **受け入れるリスク**：再認証を突破した攻撃者は、本人の他のパスキーを 1 本を残して失効させられる。自分の追加したパスキーだけを残されると、本人は締め出される。本人は締め出されたことには気付けるので、管理者による復旧（下記）で戻す。失効はすべて監査ログに残る。
- **同期型のパスキーの限界**：同期型のパスキーは複数の端末で同じ credential を共有するので、1 台だけを止めることはできない。端末を失くしたときに止めるべきなのは、同期元のアカウント側である。
- **記録**：§4.1 は、結び付けた認証器と、そのライフサイクルの出来事の日時を記録しなければならない（SHALL）としている。`credentials` に作成日時と追加の経路（`enroll` か `self`）を持ち、管理者は `user_get` で一覧できる。本人による結び付けと失効は IdP の Worker が、管理者による失効は管理用の Worker が監査ログに書き、管理者は `audit_tail` でいつでも確認できる（[データモデル](data-model.md)参照）。

**復旧**

全端末のパスキーを使えなくなったときの復旧は、管理者が発行する登録リンクだけで行う。本人がサインインできない以上、本人による追加は使えない。

1. 管理者が本人と対面で状況を確認し、`user_get` で一覧を見て、失くしたパスキーを特定する。
2. 管理者が新しい登録リンクを発行して渡す。
3. 本人が新しいパスキーを登録する（追加として扱われる）。
4. 管理者が、失くしたパスキーを `passkey_revoke` で 1 本ずつ失効させる。§4.2 の中で、侵害された認証器は速やかに停止、無効化、破棄しなければならない（SHALL）とされている。

通常は、この順（先に登録し、後で失効させる）で進める。新しいパスキーが先にあるので、失くしたパスキーをすべて失効させても 0 本にならない。

パスキーが上限（[実装に依存しない契約](cross-language-contract.md)参照）に達している場合は、上限が登録リンクによる登録にも適用され、`enroll_link_issue` も発行を拒否するので、手順 2 の前に、失くしたパスキーを `passkey_revoke` で上限未満まで失効させる。このとき 0 本にはしない（`passkey_revoke` も最後の 1 本は失効できない）。その後、手順 2 から進め、手順 4 で残りの失くしたパスキーを失効させる。

管理者による `passkey_revoke` も、本人による失効と同じく、そのユーザーのパスキーが 2 本以上あるときだけ、削除と同じ文の条件で本数を確かめて失効させる。人の操作の誤りでユーザーを 0 本にしないためである。ユーザーを完全に締め出すときは、パスキーを失効させ切るのではなく、`user_disable` を使う。ユーザーは削除しない（[データモデル](data-model.md)参照）。

§4.2 は復旧の方法として、保存型や発行型の復旧コード、復旧の連絡先、身元確認のやり直しのどれかを提供しなければならない（SHALL）としつつ、CSP の担当者とのやり取りのような独自の方法を、リスク分析に基づいて記録したうえで使ってよい（MAY）としている。この IdP は、管理者が本人を直接知っている家族規模の運用を前提に、対面での確認と登録リンクの受け渡しを独自の方法として使う。復旧コードは発行しない。

**NIST の通知要件の例外**

§4.1.2.1 は、認証器を追加したとき、追加とは独立した経路で本人に通知しなければならない（SHALL）としている。§4.6 は通知の宛先（メールアドレス、電話番号など）を 2 つ以上持たなければならない（SHALL）とし、§4.2 は復旧のときにも通知を求めている。この IdP は個人情報を持たない方針（[設計の概要](README.md)の設計原則 7）で通知の宛先を持たないので、これらの要件には従わない。例外として次のように補う。

- 本人による追加は、直前の再認証で予防する。通知は事後の検知の手段であり、通知が守る「セッションを盗まれて認証器を足される」脅威は、再認証で事前に防ぐ。
- 復旧は管理者と本人の対面で行うので、本人はその場で出来事を知っている。
- 本人への通知はしないが、パスキーの結び付けと失効はすべて監査ログに残り、管理者はいつでも `audit_tail` と `user_get` で確認できる。再認証を突破した攻撃者が追加したパスキーに気付く手段は、管理者のこの確認だけであることを受け入れる。管理者は管理 API でこの行を偽造も削除もできないが、D1 の API トークン（break-glass の基盤の権限）を持つ人なら偽造も削除もできる。その限界も受け入れるリスクとして扱う（[管理 CLI と管理用の Worker](idpctl.md)参照）。

**登録リンクの有効期限**

- 登録リンクは、管理者のもとで発行した値を本人の端末に持ち込み、パスキーを結び付けるためのものなので、NIST SP 800-63B-4 の「Binding Across Endpoints」の binding code の上限に合わせる。binding code は 1 回しか使えず（SHALL）、有効期間は最大 10 分で（SHALL）、メールのような安全でない経路で伝えてはならない（SHALL NOT）。
- 10 分は、パスキーを失くしたときの復旧として見た場合の、§4.2 の recovery code の上限のうち厳しいほう（SMS や音声で送るときの 10 分）にも収まる。
- トークンは 256 bit の乱数で、求められる強度を大きく上回る。

**画面と言語**

- 静的アセットのページは、サインインページ、登録ページ、アカウントページ（パスキーの一覧、追加、失効、サインアウト）の 3 つ。Worker が描くページは、`/authorize` のエラーページ（無効な client を含む）だけにする。
- UI のフレームワークは使わない。ページは TypeScript で書き、Vite でビルドする（`cf` が Cloudflare Vite plugin で Vite を使うので、新しい道具は増えない。[デプロイと設定](deployment.md)参照）。要求と応答の型は共有コアと共有する。
- CSP は `default-src 'self'` と `frame-ancestors 'none'` にし、インラインのスクリプト、外部のフォント、画像、アクセス解析は使わない。
- エラーの表示は汎用の文と、問い合わせのためのエラーの種類だけにし、内部の詳細を出さない。
- キーボードだけで操作でき、入力欄にラベルがあり、エラーが支援技術に読み上げられるようにする。
- 対象のブラウザが決まったら、WebAuthn Level 3 の `PublicKeyCredential.parseCreationOptionsFromJSON()`（§5.1.8）、`parseRequestOptionsFromJSON()`（§5.1.9）、`toJSON()`（§5.1）を使い、options と応答の手書きの変換を減らすことを検討する。

UI は多言語にする（ページと、Worker のエラーページの両方）。

- 最初の言語は英語と日本語。文言は言語ごとの辞書のファイルに置き、言語を足すときは辞書を足すだけで済むようにする。
- 言語は、認可リクエストの `ui_locales`、ブラウザの言語（`Accept-Language` か `navigator.languages`）、既定の英語の順に決める。OIDC Core §3.1.2.1 は、`ui_locales` の一部または全部に OP が対応していなくてもエラーにすべきでない（SHOULD NOT）としているので、対応しない言語はエラーにせず、次の候補に進む。
- `/authorize` を処理する Worker が言語を決め、`authorize_requests` に保存して、サインインページに URL のクエリで渡す。ページはクエリがなければ `navigator.languages` から決める。
- 登録ページとアカウントページは RP から来ないので、`navigator.languages` から決め、言語の切り替えを置く。
- Worker のエラーページは、同じ順でサーバー側で言語を決める。
- 管理 API の problem details は英語のままにし、多言語化の対象にしない（[管理 CLI と管理用の Worker](idpctl.md)参照）。

サインインページは、ボタンで始めるセレモニーと、条件付きメディエーション（パスキーの自動入力。WebAuthn Level 3 §5.1.4 の `mediation: "conditional"`）の両方を出す。

- ページの読み込みごとにチャレンジを 1 つ受け取り、今と同じく認可リクエストに紐付ける。ボタンのセレモニーは同じチャレンジを使い、始める前に条件付きの要求を中止する。
- 条件付きメディエーションを使う前に、ブラウザが対応しているかを確かめる（§5.1.4 は `isConditionalMediationAvailable()` か `getClientCapabilities()` で先に確かめるべき（SHOULD）としている）。
- **受け入れるコスト**：サインインページを開くだけで、チャレンジを 1 行 D1 に書く（[無料枠](free-tier.md)参照）。

**サインアウト**

- 利用者は `POST /logout`（同一オリジン確認付き）で IdP のセッションを終了できる。セッション行を削除し、Cookie も消す。
- 管理者は `idpctl` の `session_revoke` で、ユーザーの全セッションを失効させられる。`user_disable` も、そのユーザーの全セッションを削除する。
- `passkey_revoke`（管理者）と本人による失効は、ユーザーの全セッションではなく、失効させたパスキーから作ったセッションだけを外部キーの連鎖で削除する。別のパスキーから作ったセッションは残る。
- RP-Initiated Logout などの OIDC のログアウト仕様は、v1 では実装しない。
