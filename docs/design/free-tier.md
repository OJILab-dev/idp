# 無料枠の見積もりと制約

家族規模の利用なら、どの上限にも大きな余裕がある。注意が必要なのは、実測で確かめる CPU 時間と、意図的な大量リクエストで 1 日のリクエスト上限を使い切られること（後述）の 2 つ。

| 項目 | 無料枠の上限 | 見込み |
| --- | --- | --- |
| Worker のリクエスト | 10 万件 / 日 | 数百件 / 日 |
| CPU 時間 | 10 ms / リクエスト（D1 やネットワークの待ちは含まない） | WebAuthn 検証とトークンの Ed25519 署名が各数 ms の見込み。RSA 4096 bit の RS256 署名は、`RS256` を登録した client の ID トークンだけにかかる。要実測（[未決事項](open-questions.md)参照） |
| Worker のサイズ | 圧縮前 64 MiB（圧縮後の上限はない。Cloudflare「Workers Limits」） | Hono と、共有コアが WebCrypto で実装する WebAuthn の検証と JWS で、余裕の見込み（[技術選定](technology.md)参照） |
| Worker の起動時間 | 1 秒 | 問題なしの見込み |
| D1 の読み取り | 500 万行 / 日 | 少量 |
| D1 の書き込み | 10 万行 / 日 | サインイン 1 回で約 10 行。5 人が 1 日 20 回でも約 1,000 行。サインインページは読み込みのたびにチャレンジを 1 行書く（条件付きメディエーションのため。[認証フロー](authentication.md)参照）。これは認証前の書き込みで、下の受け入れるリスクの対象になる |
| D1 の DB サイズ | 500 MB / DB | 十分。ユーザー、client、グループと有効・無効の出来事は削除しないが、家族規模では小さい |
| Workers Logs | 今は 20 万イベント / 日で 3 日保持。2026 年 12 月 1 日からは 0.5 GB / 日で 7 日保持、上限に達すると UTC 0 時まで取り込まない | 障害の調査にだけ使う。状態の変化は `audit_log` に残す（[デプロイと設定](deployment.md)のログを参照） |

- サインインページ、登録ページ、アカウントページ（`/account`）は Workers の静的アセットとして置くが、すべてのリクエストで Worker を先に動かす（`run_worker_first` を真にする）。Worker は、ホスト名、スキーム、TLS のバージョンを確かめてから、静的アセットのバインディングでページを返す。理由は、IdP がゾーンのルール（シングルリダイレクトと Always Use HTTPS）を持たない（[ドメインの置き場所](domain-placement.md)の共存の設計の 3）ので、Worker が見ないリクエストは、平文の HTTP でも TLS 1.2 未満でも、そのままページが返ってしまうため。
- この選択の費用：静的アセットへのリクエストは本来は無料かつ無制限で 1 日のリクエスト上限に数えられないが、`run_worker_first` に一致したリクエストは Worker を起動するので上限に数えられ、無料枠では 429 を返されることもある（Cloudflare「Workers Static Assets」の「Billing and limitations」）。ページを初めて読み込むと、HTML、スタイルシート、ページのスクリプト、共通のスクリプトの 4 件が Worker に届く。サインイン 1 回では、`/authorize`、ページの 4 件、`/webauthn/auth/options`、`/webauthn/auth/verify`、`/authorize/resume` の約 8 件になる。2 回目からは、ブラウザーがスクリプトとスタイルシートをキャッシュから使うので（下のキャッシュ）、ページの分は HTML の 1 件だけになり、約 5 件になる。ページを純粋なアセットにしていたときの約 4 件とほぼ同じ。家族規模（1 日に数十回のサインイン）では数百件で、10 万件に対して余裕は変わらない。攻撃に対しては、もともと存在しないパスへの要求で Worker を起動できたので、上限を使い切らせる手段は増えない。
- 対象をページのパスだけに絞る形（`run_worker_first` にパスの一覧を渡す）は採らない。パスでしか選べず、スキームでは選べないので、平文の HTTP の要求のうち一覧にないもの（スクリプトとスタイルシート）は Worker を通らずに返る。ページの HTML がすべて HTTPS でしか返らなければ実害は小さいが、例外の説明が要る形より、すべてを Worker に通す単純な形を選んだ。
- ページは書き込みをしないので、Worker の Rate Limiting バインディング（下）では数えない。数えると、ページの読み込み 1 回の 4 件だけで仮の上限（10 秒あたり 10 件）の半分を使い、正規の利用を拒否しかねない。
- キャッシュ：Worker は、公開のサブリソースだけをブラウザーにキャッシュさせ、ページを見るたびの再取得で 1 日の上限（A2 ではサービスと共有）を使わないようにする。名前に内容のハッシュを持つ Vite のスクリプトとスタイルシート（`/assets/` の下）は、名前が同じなら中身も同じなので、1 年の `immutable` にする。ハッシュのない `/style.css` は、デプロイの変更が 1 時間以内に届くよう 1 時間にする。対象は、この 2 種類のパスへの `GET` と `HEAD` の成功した応答で、HTML でも `Set-Cookie` 付きでもないものだけ。どれも全員に同じ公開の内容で、秘密や利用者ごとの値を含まない。HTML のページ、エラーのページ、API の応答（トークン、discovery、JWKS を含む）、見つからない応答は、すべて `no-store` のまま。キャッシュする応答にも、ほかのセキュリティヘッダーは付ける。
- CSP の `frame-ancestors` や `Referrer-Policy` などのセキュリティヘッダーは、Worker のコードで、ページを含むすべての応答に付ける。`_headers` ファイルにも同じ値を残す。Worker を先に動かさない設定に戻ったときに、ページからヘッダーが落ちないようにするため。
- ホスト名、アカウント、D1 のリージョンなどデプロイ先の決めごとは、[デプロイと設定](deployment.md)にまとめる。

**上限を使い切らせる攻撃への備え**

Worker に届いたリクエストは、エラーで返しても 1 日 10 万件の上限に数えられる。IdP はゾーンのルールを持たない（[ドメインの置き場所](domain-placement.md)の決定 ③）ので、Worker に届く前に止める仕組みはない。IdP の 2 つの Worker のホスト名へのリクエストは、すべて Worker に届き、上限に数えられる。

- **失った保護**：以前の設計は、WAF のレート制限ルール（無料プランではゾーンに 1 つ）で IdP のパスへの大量の要求を Worker の前で止め、1 日のリクエスト上限を守っていた。また、管理用のホスト名では、mTLS の WAF のカスタムルールで、有効な証明書のない要求を Worker の前で止めていた。どちらもゾーンのルールセットに置くもので、ゾーンをサービスと共有するときは IdP が持てない（[ドメインの置き場所](domain-placement.md)の決定 ③）ので外した。そのため、1 日のリクエスト上限を大量の要求から守る仕組みは、今の設計には何もない。
- IdP の Worker は、Workers の Rate Limiting バインディングで、接続元の IP ごとに 10 秒あたりの件数を数え、超えた要求を 429 で拒否する（仮の値で 10 件）。数えるのは Worker が自分で答えるパス（`/authorize`、`/token`、`/userinfo`、`/logout`、`/jwks`、discovery、`/webauthn/*`）で、静的なページ（上）は数えない。アカウントページが呼ぶ API（`/webauthn/credentials`、`/webauthn/add/*`、`/webauthn/revoke/*`）も `/webauthn/*` に含まれる。Worker に届いた後なので 1 日のリクエスト上限は守らないが、認証前の D1 の書き込み（チャレンジの行）と CPU 時間を守る。ゾーンのプランによらず、IdP のホスト名だけに効き、サービスのホスト名には効かない。数えは Cloudflare の拠点ごとで結果整合なので、上限を超えることがある（Cloudflare「Rate Limiting」（Workers のバインディング））。バインディングがないか呼び出しが失敗したら要求を拒否する（fail-closed）。Workers Free で使えるかと料金はドキュメントに書かれていないので、最初のデプロイで確かめる（[未決事項](open-questions.md)参照）。
- 管理用の Worker にはバインディングを置かない。管理用の Worker は、許可リストにある証明書の要求だけを処理し、それ以外はホスト名、スキーム、TLS のバージョン、証明書の確認で、D1 に触れずに拒否する。バインディングで守れるのは D1 の書き込みと CPU 時間だけで、拒否される要求はどちらもほとんど使わず、1 日の上限はバインディングでは守れない。許可リストの管理者の操作を数えても、守るものがなく、`idpctl` の連続した操作（一覧の取得など）を止める害だけが残る。名前空間の ID というデプロイごとの入力も 1 つ増える。
- 1 日のリクエスト上限はアカウント全体で数えるので、管理用の Worker に届いたリクエストも IdP の上限を使う。証明書のない要求も、エッジで止まらずに管理用の Worker に届き、拒否されても上限に数えられる。IdP をサービスのアカウントに置くときは、サービスの Worker の利用も同じ上限と D1 の上限を使い、サービスへの攻撃でも IdP が止まる（逆も同じ。[ドメインの置き場所](domain-placement.md)の残るリスク）。
- Worker は監査ログに失敗の行を書かない（[データモデル](data-model.md)参照）。認証前のリクエストの失敗は、監査ログの行では D1 の書き込み上限を消費しない。ただし、サインインページが読み込みのたびに書くチャレンジの行は、認証前の正規の書き込みで、バインディングの上限より下の速さの要求で消費される（下の受け入れるリスクを参照）。
- しきい値（10 秒あたりの件数）は、正規のサインイン 1 回で発生するリクエスト数を実測して決める。
- ゾーンを IdP だけで使う fork や、ゾーンの持ち主が合意したデプロイでは、WAF のレート制限ルールをゾーンの持ち主が置いてよい。IdP のリポジトリはその定義を持たず、置くかどうかはゾーンの持ち主の判断にする。IdP の安全性は、そのルールがあってもなくても変わらない。
- Worker のルートは fail closed にする。上限を超えたときに Worker を素通しする fail open は、IdP では認証を迂回させかねないため使わない（設計原則 4）。
- **受け入れるリスク**：無料枠では、意図的な攻撃に対する可用性を保証しない。1 日のリクエスト上限は、IdP の Worker と管理用の Worker のどちらのホスト名への要求でも、1 つの IP から使い切れる。Worker の前で止める仕組みがないので、10 万件の要求を送れば、拒否されても上限に達し、アカウント全体の Worker（サービスの Worker も含む）が UTC 0 時まで止まる。バインディングが防げるのは、短時間に大量に送る単純な攻撃による D1 の書き込みと CPU 時間の消費まで。分散攻撃は IP 単位の制限では防げず、単一の IP でも、しきい値 N をわずかに下回るペースで送り続ければ 1 日 N × 8,640 件が届く。
- **受け入れるリスク（D1 の書き込み）**：サインインページの読み込みと `/webauthn/auth/options` の呼び出しは、認証前に D1 にチャレンジを 1 行書く。同じ計算で、1 日 N × 8,640 行の書き込みが届き、N が 12 以上なら D1 の 1 日の書き込み上限（10 万行）を超える。上限を超えると、アカウント全体で D1 のクエリができなくなり（Cloudflare「D1 Pricing」）、IdP の Worker だけでなく管理用の Worker も、翌日（UTC 0 時）のリセットまで止まる。チャレンジを D1 に置かない形（署名付きのステートレスなチャレンジ）にすれば避けられるが、チャレンジの一度だけの消費を D1 の `DELETE … RETURNING` で保証する今の設計を変えることになるので、今は採らない。可用性だけの問題で、不正なサインインを許すことはない。正規の利用で上限に近づくか、実際に止められたら、ステートレスなチャレンジへの切り替えを検討する。
- 止まった場合は、翌日（UTC 0 時）のリセットまでサインインできない。ほかのセキュリティ上の性質（不正なサインインを許さないこと）は損なわれない。
