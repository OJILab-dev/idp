# 無料枠の見積もりと制約

家族規模の利用なら、どの上限にも大きな余裕がある。注意が必要なのは、実測で確かめる CPU 時間と、意図的な大量リクエストで 1 日のリクエスト上限を使い切られること（後述）の 2 つ。

| 項目 | 無料枠の上限 | 見込み |
| --- | --- | --- |
| Worker のリクエスト | 10 万件 / 日 | 数百件 / 日 |
| CPU 時間 | 10 ms / リクエスト（D1 やネットワークの待ちは含まない） | WebAuthn 検証とトークンの Ed25519 署名が各数 ms の見込み。RSA 4096 bit の RS256 署名は、`RS256` を登録した client の ID トークンだけにかかる。要実測（[未決事項](open-questions.md)参照） |
| Worker のサイズ | 圧縮前 64 MiB（圧縮後の上限はない。Cloudflare「Workers Limits」） | Hono + SimpleWebAuthn + jose で余裕の見込み |
| Worker の起動時間 | 1 秒 | 問題なしの見込み |
| D1 の読み取り | 500 万行 / 日 | 少量 |
| D1 の書き込み | 10 万行 / 日 | サインイン 1 回で約 10 行。5 人が 1 日 20 回でも約 1,000 行。サインインページは読み込みのたびにチャレンジを 1 行書く（条件付きメディエーションのため。[認証フロー](authentication.md)参照）。これは認証前の書き込みで、下の受け入れるリスクの対象になる |
| D1 の DB サイズ | 500 MB / DB | 十分。ユーザー、client、グループと有効・無効の出来事は削除しないが、家族規模では小さい |
| Workers Logs | 今は 20 万イベント / 日で 3 日保持。2026 年 12 月 1 日からは 0.5 GB / 日で 7 日保持、上限に達すると UTC 0 時まで取り込まない | 障害の調査にだけ使う。状態の変化は `audit_log` に残す（[デプロイと設定](deployment.md)のログを参照） |

- サインインページ、登録ページ、アカウントページ（`/account`）は Workers の静的アセットとして配信する。静的アセットへのリクエストは無料かつ無制限で、1 日のリクエスト上限に数えられない。ただし `run_worker_first` に一致したリクエストは Worker を起動するので、課金対象になり、無料枠では 429 を返されることもある。そのため、この 3 つのページは `run_worker_first` の対象に含めず、純粋なアセットとして返す。ページが呼ぶ API（アカウントページなら `/webauthn/credentials` など）だけが Worker に届く。
- CSP の `frame-ancestors` や `Referrer-Policy` などのセキュリティヘッダーは、静的アセットには `_headers` ファイルで付ける。`_headers` は Worker が生成したレスポンスには効かないので、Worker のレスポンス（`/authorize` のエラーページなど）のヘッダーは Worker のコードで付ける。
- ホスト名、アカウント、D1 のリージョンなどデプロイ先の決めごとは、[デプロイと設定](deployment.md)にまとめる。

**上限を使い切らせる攻撃への備え**

Worker に届いたリクエストは、エラーで返しても 1 日 10 万件の上限に数えられる。D1 の書き込みを減らしても上限は守れないので、Worker に届く前に Cloudflare の WAF で止める。

- WAF のレート制限ルール（無料プランでは 1 つ）を、認証なしで呼べるパス（`/authorize`、`/webauthn/*`、`/logout` など）に適用する。アカウントページが呼ぶ API（`/webauthn/credentials`、`/webauthn/add/*`、`/webauthn/revoke/*`）も `/webauthn/*` に含まれる。
- Free プランのレート制限ルールの条件に使えるフィールドはパスと Verified Bot だけで、ホスト名は使えない（Cloudflare「Rate limiting rules」の Availability）。パスの条件はゾーンのすべてのホスト名に同じように効く。管理用のホスト名は、管理 API のパス（`/v1/*`）を同じルールの条件に足すことで含める。IdP の Worker は `/v1/*` を持たないので、IdP のホスト名への影響はない。
- 1 日のリクエスト上限はアカウント全体で数えるので、管理用の Worker に届いたリクエストも IdP の上限を使う。管理用のホスト名では、証明書のないリクエストを mTLS の WAF のカスタムルールで Worker に届く前に止める。Free プランで可能かは実装の前に確かめる（[未決事項](open-questions.md)参照）。
- Worker は監査ログに失敗の行を書かない（[データモデル](data-model.md)参照）。認証前のリクエストの失敗は、監査ログの行では D1 の書き込み上限を消費しない。ただし、サインインページが読み込みのたびに書くチャレンジの行は、認証前の正規の書き込みで、WAF を抜けたリクエストで消費される（下の受け入れるリスクを参照）。無料プランでは、集計は IP 単位、期間と遮断時間はどちらも 10 秒に固定される。
- しきい値（10 秒あたりの件数）は、正規のサインイン 1 回で発生するリクエスト数を実測して決める。
- Worker のルートは fail closed にする。上限を超えたときに Worker を素通しする fail open は、IdP では認証を迂回させかねないため使わない（設計原則 4）。
- **受け入れるリスク**：無料枠では、意図的な攻撃に対する可用性を保証しない。分散攻撃は IP 単位の制限では防げない。単一の IP でも、しきい値をわずかに下回るペースで送り続ければ遮断されず、しきい値 N に対して 1 日 N × 8,640 件が届く（N が 12 以上なら、それだけで上限を超える）。防げるのは、短時間に大量に送る単純な攻撃まで。
- **受け入れるリスク（D1 の書き込み）**：サインインページの読み込みと `/webauthn/auth/options` の呼び出しは、認証前に D1 にチャレンジを 1 行書く。同じ計算で、1 日 N × 8,640 行の書き込みが届き、N が 12 以上なら D1 の 1 日の書き込み上限（10 万行）を超える。上限を超えると、アカウント全体で D1 のクエリができなくなり（Cloudflare「D1 Pricing」）、IdP の Worker だけでなく管理用の Worker も、翌日（UTC 0 時）のリセットまで止まる。チャレンジを D1 に置かない形（署名付きのステートレスなチャレンジ）にすれば避けられるが、チャレンジの一度だけの消費を D1 の `DELETE … RETURNING` で保証する今の設計を変えることになるので、今は採らない。可用性だけの問題で、不正なサインインを許すことはない。正規の利用で上限に近づくか、実際に止められたら、ステートレスなチャレンジへの切り替えを検討する。
- 止まった場合は、翌日（UTC 0 時）のリセットまでサインインできない。ほかのセキュリティ上の性質（不正なサインインを許さないこと）は損なわれない。
