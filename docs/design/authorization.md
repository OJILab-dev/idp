# 認可

IdP が持つ認可は「誰がどのアプリを使えるか」（レベル 1）だけにする。アプリ内の権限や課金による制限は、アプリや別サービスに任せる。

- **付与の単位**：grant は「主体（principal）× client」の 1 種類だけで、主体はユーザーかグループのどちらか。両者を `principals` テーブルで同じに扱い、ユーザーへの付与もグループへの付与も同じ操作になる。例：`idpctl grant_add user:<id> grafana`、`idpctl grant_add group:<group_id> grafana`（グループは名前ではなく ID で指定する）
- **グループ**：グループは 0 人以上のユーザーの集合で、「家族」「sales 部」のような人についての事実を表す。特定の RP の利用者リストとしては使わない（後述の「管理の関心事」参照）。ユーザーとグループの関係は N 対 N。所属は `group_members` テーブルで持ち、外部キーで整合性を保つ。存在しないグループへの付与は外部キーで拒否されるので、打ち間違えた名前の grant は作られない。空のグループは誰にも許可を出さないので、0 人を禁止する必要はない。
- **ネストしない**：グループのメンバーはユーザーだけにする。権限の根拠が常に「直接付与」か「1 つのグループ経由」の 1 段でたどれるようにするため。
- **許可だけを持つ**：拒否のルールは置かず、使える client は直接付与とグループ経由の和集合で決まる。優先順位の解決が要らず、grant を消せば権限も確実に消える。
- **権限の広がりを見せる**：グループへの grant の追加やメンバーの追加は、複数の人の権限をまとめて広げる。共有コアが、新たに使えるようになるユーザーと client の組を計算して監査ログに残し、`idpctl` はその組を操作の結果に表示する。
- **有効なものだけを数える**：`effective_access` が数えるのは、有効なユーザー、有効な client と、グループ経由なら有効なグループの grant だけ。有効・無効は追記だけの出来事の表の最新の行で決まり、行が 1 つもないユーザー、client、グループは何も許可されない（fail-closed。[データモデル](data-model.md)参照）。ユーザー、client、グループは削除せず、無効化で止める。
- **判定の場所**：`/authorize`（コード発行前）と `/token`（コード交換時）の両方で `effective_access` を再確認する。`/userinfo` でも、アクセストークンの `sub` と `client_id` で `effective_access` を再確認する。
- **反映の遅れ**：トークンのクレームは発行時点の値で固定されるので、権限を外しても反映はアプリのセッションが切れるまで遅れる。対策として、トークンは短命にする。
- **将来の拡張**：アプリ内ロール（レベル 2）や自作 API のスコープ（レベル 3）が必要になったら、マイグレーションでテーブルを足す。ロールはトークンの宛先アプリの分だけを渡し、他のアプリの情報は含めない。
- **IdP に入れないもの**：オブジェクト単位の権限（「このアルバムは alice だけが編集できる」など）はアプリ側か、専用の認可エンジンに任せる。

**ユーザーとグループを分けるレイヤー**

| レイヤー | ユーザーとグループ | 理由 |
| --- | --- | --- |
| 判断（grant） | 分けない | RP を使わせるかの判断は、相手が 1 人か集団かで形を変えない |
| 評価（`effective_access`） | グループは展開されて消える | 結果は常に「ユーザー × client」。トークンを受け取るのもユーザーだけ |
| 存在（認証、トークン） | ユーザーだけ | パスキーと `sub` を持ち、サインインするのはユーザーだけ |
| 変化（ライフサイクル） | 分ける | ユーザーの変化は本人に関する操作、グループの変化は人についての事実の更新で、影響の広がり方が違う |

グループのメンバーの変更は「変化」のレイヤーの操作だが、「判断」のレイヤーを通じて、そのグループに付いた全 client のアクセスに効く。そのため、権限が広がる範囲を見せる。トークンにグループのクレームを載せない（[トークン設計](tokens.md)参照）のは、グループの意味を IdP の中にとどめ、RP との契約にしないためでもある。

**管理の関心事**

管理操作は、扱うものの性質で次のように分ける。分ける基準は「相手側に断らずに、自分の側だけで変えてよいか」。

- **ユーザーの管理**：「この人は誰で、どういう人か」という事実を正しく保つ。ユーザーの作成と有効化・無効化、登録リンクとパスキーとセッション、表示名、グループの作成と有効化・無効化とメンバー。RP へのアクセスを直接は決めない。ユーザーの無効化で全アクセスがなくなるのは、アクセスの判断ではなく、その前提が崩れるためである。
- **RP の管理**：client の登録、redirect URI、シークレット、client の有効化と無効化。
- **アクセスの管理**：grant。ユーザーの管理が保つ事実（ユーザーとグループ）を参照するだけで、事実を書き換えない。
- **基盤**：署名鍵、D1 の API トークン、管理者のクライアント証明書の発行、許可リストの変更を含むデプロイ。上の 3 つをすべて含む強さを持つので、`idpctl` と管理 API の外で運用者が扱う。

ユーザーの管理とアクセスの管理の間のインターフェースは、主体の ID とグループの意味だけにする。分ける深さは段階的に進める。

- データ：事実の表（`users`、`groups`、`group_members`）と判断の表（`client_access`）を分ける。実施済み。
- 操作：管理操作をこの区分で分類し、共有コアの操作の分類のメタデータに持つ。将来別の入り口（MCP など）に出す範囲は、この分類と[操作とリスク](operations-and-risks.md)の影響の広さで決める。
- 権限：区分ごとに別の人に持たせ、サーバー側で強制する。運用者が 1 人のうちは行わない（[将来拡張](future-extensions.md)参照）。

RP の管理とその RP へのアクセスの管理は、将来権限を分けるときには、その RP を登録した人が持つ。RP 専用の利用者リストが必要になったら、事実としてのグループとは別の概念として、アクセスの管理の側に足す。
