# 認可

IdP が持つ認可は「誰がどのアプリを使えるか」（レベル 1）だけにする。アプリ内の権限や課金による制限は、アプリや別サービスに任せる。

- **付与の単位**：ユーザーに直接付ける（`client_user_access`）か、グループに付ける（`client_group_access`）。例：`idpctl grant add group:family grafana`
- **グループ**：グループは 1 つ以上の client の集合で、ユーザーはグループに所属して、その client をまとめて使えるようになる。ユーザーとグループの関係も、グループと client の関係も N 対 N なので、どちらもテーブル（`group_members`、`client_group_access`）で持ち、外部キーで整合性を保つ。グループはネストしない。権限の根拠が常に「直接付与」か「1 つのグループ経由」の 1 段でたどれるようにするため。
- **許可だけを持つ**：拒否のルールは置かず、使える client は直接付与とグループ経由の和集合で決まる。優先順位の解決が要らず、grant を消せば権限も確実に消える。
- **判定の場所**：`/authorize`（コード発行前）と `/token`（コード交換時）の両方で `effective_access` を再確認する。`/userinfo` でも、アクセストークンの `sub` と `client_id` で `effective_access` を再確認する。
- **反映の遅れ**：トークンのクレームは発行時点の値で固定されるので、権限を外しても反映はアプリのセッションが切れるまで遅れる。対策として、トークンは短命にする。
- **将来の拡張**：アプリ内ロール（レベル 2）や自作 API のスコープ（レベル 3）が必要になったら、マイグレーションでテーブルを足す。ロールはトークンの宛先アプリの分だけを渡し、他のアプリの情報は含めない。
- **IdP に入れないもの**：オブジェクト単位の権限（「このアルバムは alice だけが編集できる」など）はアプリ側か、専用の認可エンジンに任せる。
