# Rust 移行計画

下の 4 条件がそろったら、Worker をエンドポイント単位で段階的に Rust に置き換える。判定するのは、実装言語に依存しない e2e テストと OpenID Foundation の適合性テストスイート。

**移行の準備条件**

- [ ] WebAuthn の検証：Wasm で動く成熟した RP ライブラリがある。または、自前実装が仕様のテストベクタとファジングを通っている
- [ ] RS256 の署名：WebCrypto 経由で署名できる。または `rsa` クレートの Marvin Attack 対策が安定版で出ている
- [ ] サイズと起動時間：無料枠の上限（圧縮後 3 MB、起動 1 秒）に収まる
- [ ] バインディング：使っているもの（D1、Secret）がすべて workers-rs で使える

**今のうちに守る書き方**

- DB には仕様で決まった形式だけを保存し、JS ライブラリ固有の形式は使わない（[TypeScript と Go の契約](cross-language-contract.md)参照）。
- サインインや登録の画面は静的アセット（HTML / JS）にして、Worker は JSON API とリダイレクトだけを返す。書き換えの範囲がサーバーのロジックだけで済む。
- コアのロジック（authorize リクエストの検証、認可コード交換の判定など）は D1 や fetch に触れない純粋関数にし、エラーは例外ではなく判別可能な union で返す。
- 使うバインディングは最小限に絞り、それ以外の機能はインターフェース越しに 1 か所へ閉じ込める。
- e2e テストは IdP を外から叩くブラックボックス形式で書く（HTTP と、仮想オーセンティケータを使ったブラウザ操作）。

**段階移行の順番**

Workers のルートはパス単位で別の Worker に割り当てられる。同じ D1 と署名鍵を両方にバインドし、リスクの低い順に切り替える。

1. `/.well-known/openid-configuration` と `/jwks`（読み取りだけで署名なし）
2. `/userinfo`（トークン検証だけ）
3. `/token`（RS256 の署名が入る）
4. `/authorize` とパスキーの処理（最もクリティカル）

各段階で同じ e2e テストを流し、問題があればルートを戻してロールバックする。
