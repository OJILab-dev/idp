# Rust 移行計画

下の 4 条件がそろったら、IdP の Worker をエンドポイント単位で段階的に Rust に置き換える。判定するのは、実装言語に依存しない e2e テストと OpenID Foundation の適合性テストスイート。

**移行の準備条件**

- [ ] WebAuthn の検証：Wasm で動く成熟した RP ライブラリがある。または、自前実装が仕様のテストベクタとファジングを通っている
- [ ] トークンの署名：Ed25519 を WebCrypto 経由で署名・検証できる。RS256 を有効にしたデプロイでは、RS256 も WebCrypto 経由で署名できる。または `rsa` クレートの Marvin Attack 対策が安定版で出ている
- [ ] サイズと起動時間：無料枠の上限（圧縮前 64 MiB、起動 1 秒）に収まる
- [ ] バインディング：使っているもの（D1、Secret）がすべて workers-rs で使える

**今のうちに守る書き方**

- DB には仕様で決まった形式だけを保存し、JS ライブラリ固有の形式は使わない（[実装に依存しない契約](cross-language-contract.md)参照）。
- サインインや登録の画面は静的アセット（HTML / JS）にして、Worker は JSON API とリダイレクトだけを返す。書き換えの範囲がサーバーのロジックだけで済む。
- 共有コアのロジック（authorize リクエストの検証、認可コード交換の判定など）は D1 や fetch に触れない純粋関数にし、エラーは例外ではなく判別可能な union で返す。
- 使うバインディングは最小限に絞り、それ以外の機能はインターフェース越しに 1 か所へ閉じ込める。
- e2e テストは Playwright で、IdP を外から叩くブラックボックス形式で書く（HTTP と、仮想オーセンティケータを使ったブラウザ操作）。

**共有コアと管理系の扱い**

- IdP の Worker を Rust に移すときは、その Worker が使う利用者向けの規則（パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、利用者向けの入力の検証など）を Rust で実装し直す。新しい実装は、[実装に依存しない契約](cross-language-contract.md)のテストベクタ、e2e テスト、D1 アダプタの適合テストを通ってから切り替える。
- 管理用の Worker は TypeScript の共有コアのまま残す。管理用の Worker を Rust に移すかは、IdP の Worker とは別に判断する。
- `idpctl` は管理 API の HTTP の契約だけに依存するので、サーバー側の言語が変わっても影響を受けない。
- 移行した後は、IdP の Worker と管理用の Worker が共有する規則（パスキーの上限、監査ログの行の形など）が、Rust と TypeScript の 2 つの実装になる。この重複は、契約のテストベクタと e2e テストで同じ結果になることを確かめて抑える。

**今のうちに規則を 1 つにまとめる判断**

将来 Rust に移すと規則が再び 2 つの実装になるとしても、今は規則を TypeScript の共有コア 1 つにまとめる。

- 今の重複は確定した事実で、将来の Rust 移行は上の 4 条件がそろっていない仮説である。設計は確定した事実に対して厳格にし、未確定の将来要件は契約を壊さずに後から決められる余白として残す（[現在の確実性のレベルで設計する](../philosophy/system-design/design-at-current-certainty.md)）。
- 手で保守する規則の複製は、派生物ではなく競合する第 2 の権威になり、時間とともに元の定義からずれる（[唯一の事実源](../philosophy/system-design/single-source-of-truth.md)）。2 つの Worker がパスキーと監査ログを書く今、その複製を置かない利点は、将来の書き直しのときに 1 か所を移しやすいことより大きい。
- 移行のときに規則を書き直す範囲は、IdP の Worker が使う利用者向けと関心ごとのモジュール、および標準パッケージに限られ、境界は CI の依存の lint で保たれている（[技術選定](technology.md)参照）。

**段階移行の順番**

Workers のルートはパス単位で別の Worker に割り当てられる。同じ D1 と署名鍵を両方にバインドし、リスクの低い順に切り替える。

1. `/.well-known/openid-configuration` と `/jwks`（読み取りだけで署名なし）
2. `/userinfo`（トークン検証だけ）
3. `/token`（Ed25519 と、有効なら RS256 の署名が入る）
4. `/authorize` とパスキーの処理（最もクリティカル）

各段階で同じ e2e テストを流し、問題があればルートを戻してロールバックする。
