# 将来拡張

拡張はすべて IdP の外側に足すか、マイグレーションで最小限に足す。IdP 本体に書き込み経路を増やす拡張は、そのたびに攻撃面が戻ってくることを意識して判断する。

**ledger / entitlements（課金状態）**

- 別の Worker と別の D1 で作る。結合キーは `iss` + `sub` で、メールアドレスは使わない。
- ledger は支払い・返金・付与を追記だけで記録し、「今何が使えるか」は entitlements テーブルとして導出する。
- アプリは有償機能を使う前に entitlements に問い合わせる。サーバー間なら Service Bindings で、ブラウザから直接なら、その API 用のアクセストークン（レベル 3）が必要になる。
- 「課金していない人はアプリに入れない」は IdP ではやらない。IdP のアクセス可否は「会員かどうか」に留め、課金によるゲートはアプリか entitlements 側に置く。
- 決済の webhook は署名を検証し、イベント ID で冪等にし、届く順序はバラバラな前提で扱う。
- アカウント削除時も、会計記録は `sub` のまま ledger に残す（法定の保存期間は別途確認）。

**管理コンソール**

- コンソール自体を IdP の OIDC クライアントにする（例：`idpctl grant add group:admin console`）。
- IdP のデータは Service Binding 経由の読み取り専用の関数で見せる。IdP の D1 を直接バインドしない。
- IdP への書き込みは当面 CLI のまま。コンソールから書けるようにする場合は、管理操作の直前にパスキーの再確認（ステップアップ）を入れる。

**その他**

- リフレッシュトークン：SPA やモバイルアプリが必要になったら、ローテーションと再利用検知付きで追加する。リフレッシュ時にもアクセス可否を再確認する。
- 認可レベル 2・3：`roles` クレーム（宛先アプリの分だけ）と、`resource` + スコープの積集合による API 用トークン。未登録の resource は拒否する。
- リモート MCP：スマホなどから管理したくなった場合だけ検討する。MCP 用の OAuth 対応とステップアップが必要になる。
