# 将来拡張

拡張はすべて IdP の外側に足すか、マイグレーションで最小限に足す。IdP 本体に書き込み経路を増やす拡張は、そのたびに攻撃面が戻ってくることを意識して判断する。

**ledger / entitlements（課金状態）**

- 別の Worker と別の D1 で作る。結合キーは `iss` + `sub` で、メールアドレスは使わない。
- ledger は支払い・返金・付与を追記だけで記録し、「今何が使えるか」は entitlements テーブルとして導出する。
- アプリは有償機能を使う前に entitlements に問い合わせる。サーバー間なら Service Bindings で、ブラウザから直接なら、その API 用のアクセストークン（レベル 3）が必要になる。
- 「課金していない人はアプリに入れない」は IdP ではやらない。IdP のアクセス可否は「会員かどうか」に留め、課金によるゲートはアプリか entitlements 側に置く。
- 決済の webhook は署名を検証し、イベント ID で冪等にし、届く順序はバラバラな前提で扱う。
- アカウント削除時も、会計記録は `sub` のまま ledger に残す（法定の保存期間は別途確認）。

**管理コンソールと管理権限の分離**

- 管理系は IdP の OIDC クライアントにしない。次の理由による。
  - 管理権限を IdP の grant で表すと、grant を書ける人が自分を管理者にでき、権限の根拠が守る対象の中に閉じる。
  - IdP の認証やトークン発行の欠陥が、そのまま管理権限の奪取になる。今は管理権限が Cloudflare の側にあり、IdP の欠陥と切り離されている。
  - IdP に入れなくなる障害のとき、それを直す管理系にも入れない。
  - 管理用のエンドポイントをインターネットに出すことになる。
- 管理の権限を人ごとに分ける必要が出たら（[認可](authorization.md)の管理の関心事を参照）、管理用の Worker を別に置き、D1 にはその Worker だけが触れるようにする。`idpctl` は D1 の API トークンを持たず、管理用の Worker を呼ぶ。
- 管理用の Worker は、IdP が発行したトークンではなく、管理者ごとの独立した認証（管理者ごとの鍵など）で利用者を確かめ、ユーザーの管理と RP・アクセスの管理の権限をサーバー側で強制する。基盤の権限はこの Worker の外（Cloudflare と 1Password）に置いたままにする。
- RP の管理とその RP へのアクセスの管理は、その RP を登録した人が持つ。どの主体がどの client を所有するかの表をマイグレーションで足し、所有者がいなくなったときに付け替える手段も用意する。
- IdP のデータを見せる画面が必要なら、Service Binding 経由の読み取り専用の関数で見せる。IdP の D1 を直接バインドしない。

**その他**

- リフレッシュトークン：ネイティブアプリ・モバイルアプリ（public client）が必要になったら、ローテーションと再利用検知付きで追加する。リフレッシュ時にもアクセス可否を再確認する。
- 認可レベル 2・3：`roles` クレーム（宛先アプリの分だけ）と、`resource` + スコープの積集合による API 用トークン。未登録の resource は拒否する。
- リモート MCP：スマホなどから管理したくなった場合だけ検討する。MCP 用の OAuth 対応とステップアップが必要になる。その認可サーバーに IdP 自身は使わない（上の「管理コンソールと管理権限の分離」と同じ理由）。
