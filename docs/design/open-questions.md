# 未決事項・要検証

実装に入る前に決めるものと、作りながら実測で確かめるものがある。

**決めること**

- [ ] ID の形式（UUIDv7 か ULID か）
- [ ] ハッシュのエンコーディング（hex か base64url か）
- [ ] セッションの有効期限（例：30 日のスライディングにするか、絶対期限を設けるか）
- [ ] 登録リンクの有効期限
- [ ] ID トークンとアクセストークンの有効期限を 5〜10 分で確定するか
- [ ] e2e テストの道具（chromedp か Playwright か）
- [ ] 正式な OpenID Certified を取得するか（費用あり。テストの全項目合格は必須）
- [ ] 監査ログのテーブルのスキーマ（カラム、操作者、対象、時刻の形式）。`idpctl` が書く値の形を、[TypeScript と Go の契約](cross-language-contract.md)の一部として固める
- [ ] JWKS を長くキャッシュする RP のために、次の署名鍵を前もって JWKS に載せておくか。current と previous の方式でも、新しい公開鍵が遅くともその鍵で署名する最初のトークンと同時に JWKS に載っていれば仕様に準拠する（OIDC Core §10.1。§10.1.1 は待機期間を定めず、見慣れない `kid` を見た検証側が JWKS を取り直すとしている）。仕様の要求ではなく、RP 側の頑健さのための判断
- [ ] 署名鍵を誰がどこで生成し、どこにバックアップするか。Worker Secret は書き込み専用で読み出せないので、Secret だけに置くと再設定や移行のときに取り出せない
- [ ] D1 のバックアップと障害時の復旧手順。Time Travel（一定期間の任意の時点に戻せる）に任せるか、定期的な export を手元に取るか

**実測・確認すること**

- [ ] 無料枠の CPU 10 ms に、WebAuthn 検証と RS256 署名が収まるか
- [ ] Ed25519（-8）のパスキーを、Workers の WebCrypto（標準の Ed25519）で検証できるか
- [ ] OpenID Foundation の Basic OP と Config OP のテストプランを全項目合格するか
- [ ] D1 REST API のバッチが、途中で失敗したときに全体をロールバックするか（わざと 2 文目を失敗させて確認）
- [ ] Worker のバンドルサイズが 3 MB（圧縮後）に十分収まるか
- [ ] 正規のサインイン 1 回で Worker に届くリクエスト数（WAF のしきい値の根拠）
- [ ] WAF のレート制限で遮断したリクエストが、Workers のリクエスト数に数えられないこと（ドキュメントには「Worker に届いたリクエストだけが数えられる」としか書かれていない。ダッシュボードの分析で確認する）
- [ ] カスタムドメインに割り当てた Worker でも fail closed を設定できるか（ドキュメントではルートの設定として説明されている）
