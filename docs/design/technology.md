# 技術選定

サーバー側（IdP の Worker、管理用の Worker、両者が使う共有コア）はすべて TypeScript で作り、D1 を操作するロジックは共有コアの 1 か所に置く。手元の管理ツール `idpctl` は、管理用の Worker の HTTPS API を呼ぶだけの Go の薄いクライアントにする。言語をまたぐ取り決めは、[実装に依存しない契約](cross-language-contract.md)として固める。

| 構成要素 | 選択 | 理由 |
| --- | --- | --- |
| IdP 本体（Worker） | TypeScript + Hono | WebAuthn の検証と JWS の署名を、外部のライブラリなしに Workers の WebCrypto だけで書け、無料枠の CPU とサイズに収まる（下の「WebAuthn の検証」参照） |
| 管理用の Worker | TypeScript | 共有コアの管理系のユースケースを、IdP 本体とは別のホスト名で HTTPS の管理 API として出す。管理者は mTLS で認証する（[管理 CLI と管理用の Worker](idpctl.md)参照） |
| 共有コア | TypeScript（`packages/core`） | ドメインの規則、入力のスキーマと検証、SQL 文、ユースケースを 1 か所に置き、2 つの Worker が同じ実装を使う（下の「コードの構成」参照） |
| 管理 CLI | Go（`idpctl`） | HTTPS のクライアントだけを持ち、ドメインの規則を評価しない。単一バイナリで配れ、mTLS のクライアント証明書を標準ライブラリで扱える |
| パッケージ管理 | pnpm の workspace | 共有コアと 2 つの Worker を 1 つのリポジトリで管理し、依存の向きを機械的に確かめられる |
| データベース | D1 | `DELETE … RETURNING` で使い捨て値を原子的に消費でき、無料枠で足りる |
| トークン署名 | Ed25519（JOSE の `alg` は RFC 9864 の `Ed25519`、WebCrypto）。RS256 は RSA の鍵を設定したときだけ有効にする任意の機能 | Ed25519 は鍵が小さく、RSA より署名が軽い。OIDC Discovery 1.0 §3 と OIDC Core 1.0 §15.1 は RS256 を必須とするので、RSA を必要とする RP をつなぐときと適合性テストでは RS256 を有効にする。無効の間の逸脱は[標準準拠](standards-compliance.md)に例外として記録する |
| e2e テスト | Playwright（ブラックボックス） | HTTP とブラウザ操作で IdP を外から叩くので実装言語に依存せず、Rust に移行しても同じテストを流せる。仮想オーセンティケータでパスキーの操作を自動化できる |
| 画面 | TypeScript + Vite（UI のフレームワークなし） | ページは 3 つだけで、CSP を `default-src 'self'` に保てる。Vite は `cf` が Cloudflare Vite plugin のために使うので、道具が増えない。要求と応答の型を共有コアと共有する（[認証フロー](authentication.md)の画面と言語を参照） |
| 基盤の構成管理 | Terraform（Cloudflare provider）と、`cf` を使うシェルスクリプト | 宣言できる基盤は Terraform、手続きの操作（マイグレーション、デプロイ、Secret の登録、鍵の生成）はスクリプトに分ける（[デプロイと設定](deployment.md)参照） |
| Worker の中のレート制限 | Workers の Rate Limiting バインディング（IdP の Worker だけ） | ゾーンの WAF のレート制限ルールは Free ではゾーンに 1 つで、ゾーンをサービスと共有すると IdP が使えないことがある。バインディングは、ゾーンのルールの持ち主やプランによらず、認証前の D1 の書き込みを守れる。近似で、Durable Objects のような厳密な数えはしないが、家族規模の IdP にそこまでは要らない（[無料枠](free-tier.md)、[ドメインの置き場所](domain-placement.md)の共存の設計の 4） |
| ストレージに使わないもの | KV | 結果整合で使い捨て値に向かず、無料枠の書き込みが 1 日 1,000 件と少ない |

**コードの構成**

pnpm の workspace に次の 4 つを置く。`idpctl` は Go なので、この workspace の外の Go モジュールとして同じリポジトリに置く。

| パッケージ | 中身 | D1 への接続 |
| --- | --- | --- |
| `packages/core` | ドメインの規則（パスキーの上限、最後の 1 本は失効できない規則、無効化されたユーザーの確認など）、入力のスキーマと検証、SQL 文、利用者向けのユースケースと `idpctl` の全 29 操作のユースケース、操作ごとの分類のメタデータ、D1 を操作するポート（インターフェース） | 触れない。ポート越しに、実行する文のバッチを渡すだけ |
| `packages/d1-adapter` | コアの D1 のポートを D1 バインディングで実装する薄いアダプタと、その適合テスト。2 つの Worker が同じものを使う | D1 バインディング（Worker から渡される） |
| `apps/worker` | IdP の Worker。`packages/d1-adapter` に D1 バインディングを渡す配線と、公開する HTTP（OIDC、パスキー API、静的アセット） | D1 バインディング |
| `apps/admin-worker` | 管理用の Worker。`packages/d1-adapter` に D1 バインディングを渡す配線、mTLS の再確認と許可リストによる管理者の確定、管理 API の HTTP | D1 バインディング（IdP の Worker と同じ D1） |

- **規則の実装は 1 つ**：IdP の Worker もパスキー（本人による追加と失効、登録リンクによる登録）と監査ログの行を書くので、パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、入力の検証は、2 つの Worker が共有する規則である。これらは共有コアにだけ実装し、アプリ側にも `idpctl` にも書き直さない。
- **スキーマは 1 つ**：各操作の入力のスキーマは共有コアで定義し、同じスキーマが入力の検証と管理 API の仕様（OpenAPI など）を決める。管理 API の仕様はこのスキーマから生成し、`idpctl` の Go の型はその仕様から生成する。手でコピーした型は置かない（[実装に依存しない契約](cross-language-contract.md)参照）。
- **入力のスキーマのライブラリは Zod v4**：スキーマは Zod v4 で書き、OpenAPI の仕様は Zod v4 が持つ JSON Schema への変換（`toJSONSchema`）から組み立てる。JSON Schema を出せることと、検証の結果をフィールドの単位で返せること（`validation-failed` の JSON Pointer の一覧に使う）が選んだ理由である。版は `minimumReleaseAge` を満たす完全な版で固定する。Zod を import するのは管理系のモジュールだけにし、共有のモジュールと利用者向けのモジュールからは import しない。IdP の Worker のバンドルに Zod を含めず、無料枠のサイズと起動の時間を圧迫しないためで、テストがこの境界を確かめる。値の形（UUIDv4、client ID、redirect URI など）の判定は共有のモジュールの関数に置き、Zod のスキーマはそれを呼ぶだけにするので、IdP の Worker と管理用の Worker で同じ値が同じ判定を受ける。
- **操作の分類はコアに置く**：各操作の分類（管理の関心事、読み取りか書き込みか、本人性を確定させるか）は、ユースケースの隣にメタデータとして定義する。今は CLI だけが使うが、将来別の入り口（[将来拡張](future-extensions.md)の MCP など）を足すときは、出す範囲をこのメタデータから決める。
- **アダプタは薄く、1 つにする**：D1 アダプタは、コアが組み立てた文のバッチを D1 バインディングの 1 回のバッチ（D1 では 1 つのトランザクション）で実行して結果を返すだけで、ドメインのロジックを持たない。アダプタが行うのは型の変換（BLOB をバイト列として渡し、バイト列として返す）と、バインディングのエラーをポートのエラーに包むことだけ。当初は Worker ごとにアダプタを置く構成にしていたが、2 つの Worker は同じ D1 を同じバインディングの API で使うので、アダプタは同じ実装になる。同じコードと適合テストを 2 か所に複製すると、片方だけ直して性質が食い違うおそれがあるため、`packages/d1-adapter` の 1 つにまとめ、両方の Worker がそれを使う。適合テスト（バッチの原子性と途中で失敗したときのロールバック、トリガーの `RAISE(ABORT, …)` によるバッチ全体のロールバック、`DELETE … RETURNING` の結果、変更行数、BLOB の往復、結果の順序と件数）は、マイグレーションを適用したローカルの D1 に対して CI で流し、アダプタの実装を変えても同じ性質が保たれることを確かめる。
- **`idpctl` は規則を評価しない**：入力の検証も、パスキーの上限などの判定も、管理用の Worker が行う。`idpctl` は引数を API の要求に組み立て、応答と管理用の Worker が返すエラーを表示するだけにする。手元で先に検証すると、規則の実装が 2 つになるため。
- **`idpctl` の置き場所**：`idpctl` は `cmd/idpctl` に、専用の `go.mod` を持つ Go モジュールとして置く。リポジトリのルートに `go.mod` を置かないのは、pnpm の workspace と Go のモジュールの境界をディレクトリで分け、TypeScript の道具が Go のファイルを、Go の道具が `node_modules` を見ないようにするため。管理 API の型とクライアントは `cmd/idpctl/internal/adminapi` に oapi-codegen で生成してコミットし、手で編集しない。生成し直してコミット済みのファイルと比べるテストを置き、仕様と生成物のずれを検出する。Go と oapi-codegen の版は、ほかの道具と同じく `mise.toml` で完全な版に固定し、公開から 14 日以上たった版だけを使う。整形、静的検査、ビルド、テスト（ずれの検出を含む）は `mise run idpctl:check` でまとめて実行し、生成し直すときは `mise run idpctl:generate` を使う。
- **生成器の制約**：管理 API の仕様は OpenAPI 3.1 で、`limit`、`since`、`until` のクエリは整数と文字列の和の型を持つ。oapi-codegen はこの和の型を外から値を設定できない形で生成するので、`idpctl` はこの 3 つだけを、生成されたクライアントの要求の編集の関数でクエリに加える。値は手元で検証せず、10 進の文字列のまま渡す。

**WebAuthn の検証**

WebAuthn の応答の検証には、ライブラリ（`@simplewebauthn/server` など）を使わない。共有コアの利用者向けのモジュールに、この IdP が必要とする範囲だけを検証する小さな検証器を置く。

- 範囲：attestation は `none` だけを受け入れる。ただし、`none` を求めてもクライアントがそのまま渡してよいとされる packed の self attestation（x5c がないもの。WebAuthn Level 3 §5.1.3）は、資格情報の公開鍵で署名を検証して受け入れる。証明書の連鎖（x5c）を持つものと、そのほかの形式は拒否する。公開鍵は COSE の -8（Ed25519）、-7（ES256）、-257（RS256 で 2048 bit 以上）だけにする。
- 確かめること：§7.1 と §7.2 の手順のうち、この IdP の options で当てはまるものはすべて行う。UV は必須にし、origin と RP ID は issuer から決まる 1 つに固定する。`clientDataJSON` の `type`、`challenge`、`origin`、`crossOrigin`、`topOrigin`、`rpIdHash`、UP・UV・BE・BS のフラグ、BE が登録の時から変わっていないこと（§7.2）、sign count の規則（[標準準拠](standards-compliance.md)参照）を確かめる。拡張は要求しないので、authenticator data の拡張は読み飛ばすだけにする。
- CBOR は、WebAuthn が使う部分集合（長さが確定していて、タグ、浮動小数点、重複したキーを含まないもの）だけを復号し、それ以外は拒否する。署名は Workers の WebCrypto で検証する。
- 理由（依存）：`@simplewebauthn/server` は、この IdP が使わない attestation の形式（証明書の連鎖、TPM、Android など）のために、ASN.1 と X.509 のライブラリを推移的に持ち込む。依存はすべて `minimumReleaseAge` の 14 日を満たす版に固定するので、推移的な依存の更新のたびに確認が要る。依存を増やさなければ、この確認がなくなる。
- 理由（サイズ）：IdP の Worker は無料枠のサイズと起動の時間に収める（[無料枠](free-tier.md)参照）。使わない形式のコードをバンドルに含めない。
- 理由（レビュー）：応答の検証は、IdP で最も危険な部分の 1 つである。必要な手順だけを数百行で書けば、全体を通して読める。ライブラリの汎用の分岐（attestation の信頼の判断や多数の形式）を読む必要もなくなる。JWS も同じ方針で、共有コアに WebCrypto で実装している。
- 受け入れるコスト：仕様の手順の実装の誤りは、自分たちで負う。そこで、手順ごとに、その手順だけを破った応答を拒否するテストを置く。テストのベクタは、テストの中で WebCrypto で生成した鍵で作り、秘密鍵をリポジトリに置かない。実際のブラウザの応答との突き合わせは、Playwright の仮想オーセンティケータを使う e2e テスト（[標準準拠](standards-compliance.md)参照）で行う。

**e2e テストの構成**

e2e テストは `e2e/` に置き、Playwright（`@playwright/test` を `minimumReleaseAge` を満たす完全な版で固定）の Chromium で、ローカルで動かした実際の IdP の Worker を外から操作する。`pnpm run e2e` で実行し、CI では専用の `e2e` job で流す。`pnpm run check` には含めない（ブラウザのダウンロードが要るため）。

- **ビルド**：Worker のモジュールと 3 つのページを、テストの前に Vite で `e2e/dist` にビルドする。`cf` は Cloudflare Vite plugin を通して Vite を使うが、plugin はまだ宣言していない（[未決事項](open-questions.md)参照）ので、e2e は同じ入力を Vite に直接渡す。`cf` と wrangler は使わない。
- **実行環境**：ビルドしたものを、`cf` が同梱する workerd を Miniflare で動かす。静的アセットの扱い（`htmlHandling`、`notFoundHandling`、`runWorkerFirst`）とバインディングは `apps/worker/cloudflare.config.ts` の設定をそのまま使い、ローカルで差し替えるのは、モジュール、アセットのディレクトリ、署名鍵、D1 だけにする。署名鍵は実行のたびにメモリ上で生成し、D1 はマイグレーションを適用した空のローカルの D1 にする。Miniflare はユーザーの Worker の有無を既定で偽とするので、明示的に真にする。
- **TLS とホスト名**：Worker は issuer が `https://<host>` でない要求を拒否する。この確認は弱めず、issuer を `https://idp.test` とし、実行のたびに openssl で生成する使い捨ての自己署名証明書（`idp.test` と RP 役の `rp.test`）で HTTPS を提供する。Chromium には、この 2 つのホスト名の 443 番ポートをローカルのポートへ向ける設定と、この証明書の公開鍵だけを信頼する設定を起動時に渡す。証明書のエラーを無視する設定は使わない。WebAuthn は証明書のエラーがあるページで動かず、本番と同じく安全なコンテキストで確かめるため。証明書と鍵は `e2e/dist` から出さず、コミットしない。
- **パスキー**：CDP の仮想オーセンティケータ（CTAP2、内蔵の transport、resident key と UV あり）を使い、ブラウザの実際の WebAuthn API を通す。仮想オーセンティケータは条件付きメディエーションの要求をクリックなしで完了させるので、ボタンの経路を確かめるテストでは、ページの読み込みの間だけオーセンティケータを外し、同じ資格情報を持つものを付け直してからボタンを押す。2 本目の追加では、再認証の後に別の端末に当たる新しいオーセンティケータに切り替える（作成の要求が既存の資格情報を除外するため）。
- **状態の用意**：ユーザー、登録リンク、confidential client と public client、付与は、共有コアの管理系のユースケースを、Worker と同じローカルの D1 に対して直接実行して作る。管理用の Worker と mTLS は通さない。パスキーは登録リンクからブラウザで登録する。
- **RP の代役**：`rp.test` の小さな HTTPS サーバーがリダイレクトを受け、テストが RP として `iss` と `state` を確かめ、`/token` でコードを交換し、`/userinfo` を呼ぶ。Playwright の要求の差し替えは使わない。Chromium はリダイレクト先の要求を差し替えの対象にしないため。
- **CSP**：すべてのテストで、ブラウザのコンソールに CSP の違反が出ないことを確かめる。検出そのものが働くことも、インラインのスクリプトを注入して確かめる。
- **並列度**：テストのワーカーは 1 つにする。ワーカーごとに workerd を起動するので、負荷の高い手元の環境と CI でタイムアウトしないようにするため。

**利用者向けと管理系の境界**

設計原則 1（攻撃面を小さくする）を、ホスト名とコードの依存の両方で守る。

- 共有コアは、利用者向けのユースケース（OIDC、パスキーの登録とサインイン、アカウントページでの本人による操作）と、管理系のユースケース（`idpctl` の操作）を別のモジュールに分ける。両方が使う規則（パスキーの上限、監査ログの行の形、入力の検証など）は、どちらにも属さない共有のモジュールに置く。
- `apps/worker` が import してよいのは、利用者向けと共有のモジュールだけにする。利用者向けのモジュールも管理系のモジュールを import しない。CI の依存の lint でこれを強制し、違反があればビルドを失敗させる。
- CI は、IdP の Worker のビルド成果物に管理系のモジュールのコードが含まれていないことも確かめる。lint の設定漏れや間接的な import があっても、成果物の側で止めるため。
- IdP の Worker は、管理操作を一切公開しない。管理操作は別のホスト名の管理用の Worker にだけ置き、エッジの mTLS で守る（[管理 CLI と管理用の Worker](idpctl.md)参照）。

**今 Rust を採らない理由**

- 実績のある WebAuthn ライブラリ webauthn-rs は OpenSSL 依存で、Workers の Wasm 環境では動かない。
- 純 Rust の `rsa` クレートは Marvin Attack（RUSTSEC-2023-0071）が未修正で、ネット越しに署名を叩ける IdP では使えない。
- 結果として、IdP で最も危険な部分を自前で書くことになる。移行の条件は[Rust 移行計画](rust-migration.md)にまとめる。

**検討して外した候補**

- Gleam：書き味は Rust に近く JS ライブラリも使えるが、FFI の型を自分で保証する必要がある。
- Go（syumai/workers）の Worker：通常の Go はバイナリが大きく無料枠に載らず、TinyGo ではライブラリの互換性が不安。
- Python Workers：無料枠の CPU 10 ms と起動 1 秒の上限に対して重い。
- `idpctl` が D1 REST API で D1 を直接操作する形：管理用のエンドポイントをインターネットに出さずに済むが、D1 を操作するロジック（パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、入力の検証）を手元のツールにも持つことになり、IdP の Worker の実装と二重になる。また、D1 の API トークンがそのまま管理者の権限になるので、操作者は自己申告になり、管理者ごとに権限や記録を分けられない。管理操作をサーバー側の共有コアに集め、管理者を mTLS で確かめる形を選んだ。
