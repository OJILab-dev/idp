# 技術選定

サーバー側（IdP の Worker、管理用の Worker、両者が使う共有コア）はすべて TypeScript で作り、D1 を操作するロジックは共有コアの 1 か所に置く。手元の管理ツール `idpctl` は、管理用の Worker の HTTPS API を呼ぶだけの Go の薄いクライアントにする。言語をまたぐ取り決めは、[実装に依存しない契約](cross-language-contract.md)として固める。

| 構成要素 | 選択 | 理由 |
| --- | --- | --- |
| IdP 本体（Worker） | TypeScript + Hono | SimpleWebAuthn と jose（WebCrypto）が成熟しており、無料枠の CPU とサイズに収まる |
| 管理用の Worker | TypeScript | 共有コアの管理系のユースケースを、IdP 本体とは別のホスト名で HTTPS の管理 API として出す。管理者は mTLS で認証する（[管理 CLI と管理用の Worker](idpctl.md)参照） |
| 共有コア | TypeScript（`packages/core`） | ドメインの規則、入力のスキーマと検証、SQL 文、ユースケースを 1 か所に置き、2 つの Worker が同じ実装を使う（下の「コードの構成」参照） |
| 管理 CLI | Go（`idpctl`） | HTTPS のクライアントだけを持ち、ドメインの規則を評価しない。単一バイナリで配れ、mTLS のクライアント証明書を標準ライブラリで扱える |
| パッケージ管理 | pnpm の workspace | 共有コアと 2 つの Worker を 1 つのリポジトリで管理し、依存の向きを機械的に確かめられる |
| データベース | D1 | `DELETE … RETURNING` で使い捨て値を原子的に消費でき、無料枠で足りる |
| トークン署名 | Ed25519（JOSE の `alg` は RFC 9864 の `Ed25519`、WebCrypto）。RS256 は RSA の鍵を設定したときだけ有効にする任意の機能 | Ed25519 は鍵が小さく、RSA より署名が軽い。OIDC Discovery 1.0 §3 と OIDC Core 1.0 §15.1 は RS256 を必須とするので、RSA を必要とする RP をつなぐときと適合性テストでは RS256 を有効にする。無効の間の逸脱は[標準準拠](standards-compliance.md)に例外として記録する |
| e2e テスト | Playwright（ブラックボックス） | HTTP とブラウザ操作で IdP を外から叩くので実装言語に依存せず、Rust に移行しても同じテストを流せる。仮想オーセンティケータでパスキーの操作を自動化できる |
| 画面 | TypeScript + Vite（UI のフレームワークなし） | ページは 3 つだけで、CSP を `default-src 'self'` に保てる。Vite は `cf` が Cloudflare Vite plugin のために使うので、道具が増えない。要求と応答の型を共有コアと共有する（[認証フロー](authentication.md)の画面と言語を参照） |
| 基盤の構成管理 | Terraform（Cloudflare provider）と、`cf` を使うシェルスクリプト | 宣言できる基盤は Terraform、手続きの操作（マイグレーション、デプロイ、Secret の登録、鍵の生成）はスクリプトに分ける（[デプロイと設定](deployment.md)参照） |
| ストレージに使わないもの | KV | 結果整合で使い捨て値に向かず、無料枠の書き込みが 1 日 1,000 件と少ない |

**コードの構成**

pnpm の workspace に次の 4 つを置く。`idpctl` は Go なので、この workspace の外の Go モジュールとして同じリポジトリに置く。

| パッケージ | 中身 | D1 への接続 |
| --- | --- | --- |
| `packages/core` | ドメインの規則（パスキーの上限、最後の 1 本は失効できない規則、無効化されたユーザーの確認など）、入力のスキーマと検証、SQL 文、利用者向けのユースケースと `idpctl` の全 29 操作のユースケース、操作ごとの分類のメタデータ、D1 を操作するポート（インターフェース） | 触れない。ポート越しに、実行する文のバッチを渡すだけ |
| `packages/d1-adapter` | コアの D1 のポートを D1 バインディングで実装する薄いアダプタと、その適合テスト。2 つの Worker が同じものを使う | D1 バインディング（Worker から渡される） |
| `apps/worker` | IdP の Worker。`packages/d1-adapter` に D1 バインディングを渡す配線と、公開する HTTP（OIDC、パスキー API、静的アセット） | D1 バインディング |
| `apps/admin-worker` | 管理用の Worker。`packages/d1-adapter` に D1 バインディングを渡す配線、mTLS の再確認と許可リストによる管理者の確定、管理 API の HTTP | D1 バインディング（IdP の Worker と同じ D1） |

- **規則の実装は 1 つ**：IdP の Worker もパスキー（本人による追加と失効、登録リンクによる登録）と監査ログの行を書くので、パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、入力の検証は、2 つの Worker が共有する規則である。これらは共有コアにだけ実装し、アプリ側にも `idpctl` にも書き直さない。
- **スキーマは 1 つ**：各操作の入力のスキーマは共有コアで定義し、同じスキーマが入力の検証と管理 API の仕様（OpenAPI など）を決める。管理 API の仕様はこのスキーマから生成し、`idpctl` の Go の型はその仕様から生成する。手でコピーした型は置かない（[実装に依存しない契約](cross-language-contract.md)参照）。
- **操作の分類はコアに置く**：各操作の分類（管理の関心事、読み取りか書き込みか、本人性を確定させるか）は、ユースケースの隣にメタデータとして定義する。今は CLI だけが使うが、将来別の入り口（[将来拡張](future-extensions.md)の MCP など）を足すときは、出す範囲をこのメタデータから決める。
- **アダプタは薄く、1 つにする**：D1 アダプタは、コアが組み立てた文のバッチを D1 バインディングの 1 回のバッチ（D1 では 1 つのトランザクション）で実行して結果を返すだけで、ドメインのロジックを持たない。アダプタが行うのは型の変換（BLOB をバイト列として渡し、バイト列として返す）と、バインディングのエラーをポートのエラーに包むことだけ。当初は Worker ごとにアダプタを置く構成にしていたが、2 つの Worker は同じ D1 を同じバインディングの API で使うので、アダプタは同じ実装になる。同じコードと適合テストを 2 か所に複製すると、片方だけ直して性質が食い違うおそれがあるため、`packages/d1-adapter` の 1 つにまとめ、両方の Worker がそれを使う。適合テスト（バッチの原子性と途中で失敗したときのロールバック、トリガーの `RAISE(ABORT, …)` によるバッチ全体のロールバック、`DELETE … RETURNING` の結果、変更行数、BLOB の往復、結果の順序と件数）は、マイグレーションを適用したローカルの D1 に対して CI で流し、アダプタの実装を変えても同じ性質が保たれることを確かめる。
- **`idpctl` は規則を評価しない**：入力の検証も、パスキーの上限などの判定も、管理用の Worker が行う。`idpctl` は引数を API の要求に組み立て、応答と管理用の Worker が返すエラーを表示するだけにする。手元で先に検証すると、規則の実装が 2 つになるため。

**利用者向けと管理系の境界**

設計原則 1（攻撃面を小さくする）を、ホスト名とコードの依存の両方で守る。

- 共有コアは、利用者向けのユースケース（OIDC、パスキーの登録とサインイン、アカウントページでの本人による操作）と、管理系のユースケース（`idpctl` の操作）を別のモジュールに分ける。両方が使う規則（パスキーの上限、監査ログの行の形、入力の検証など）は、どちらにも属さない共有のモジュールに置く。
- `apps/worker` が import してよいのは、利用者向けと共有のモジュールだけにする。利用者向けのモジュールも管理系のモジュールを import しない。CI の依存の lint でこれを強制し、違反があればビルドを失敗させる。
- CI は、IdP の Worker のビルド成果物に管理系のモジュールのコードが含まれていないことも確かめる。lint の設定漏れや間接的な import があっても、成果物の側で止めるため。
- IdP の Worker は、管理操作を一切公開しない。管理操作は別のホスト名の管理用の Worker にだけ置き、エッジの mTLS で守る（[管理 CLI と管理用の Worker](idpctl.md)参照）。

**今 Rust を採らない理由**

- 実績のある WebAuthn ライブラリ webauthn-rs は OpenSSL 依存で、Workers の Wasm 環境では動かない。
- 純 Rust の `rsa` クレートは Marvin Attack（RUSTSEC-2023-0071）が未修正で、ネット越しに署名を叩ける IdP では使えない。
- 結果として、IdP で最も危険な部分を自前で書くことになる。移行の条件は[Rust 移行計画](rust-migration.md)にまとめる。

**検討して外した候補**

- Gleam：書き味は Rust に近く JS ライブラリも使えるが、FFI の型を自分で保証する必要がある。
- Go（syumai/workers）の Worker：通常の Go はバイナリが大きく無料枠に載らず、TinyGo ではライブラリの互換性が不安。
- Python Workers：無料枠の CPU 10 ms と起動 1 秒の上限に対して重い。
- `idpctl` が D1 REST API で D1 を直接操作する形：管理用のエンドポイントをインターネットに出さずに済むが、D1 を操作するロジック（パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、入力の検証）を手元のツールにも持つことになり、IdP の Worker の実装と二重になる。また、D1 の API トークンがそのまま管理者の権限になるので、操作者は自己申告になり、管理者ごとに権限や記録を分けられない。管理操作をサーバー側の共有コアに集め、管理者を mTLS で確かめる形を選んだ。
