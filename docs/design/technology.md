# 技術選定

IdP 本体の Worker も手元の管理ツール `idpctl` も TypeScript で作り、D1 を操作するロジックは共有のコア 1 つに置く。言語やランタイムをまたぐ取り決めは、実装に依存しない契約（[実装に依存しない契約](cross-language-contract.md)）として別に固める。

| 構成要素 | 選択 | 理由 |
| --- | --- | --- |
| IdP 本体（Worker） | TypeScript + Hono | SimpleWebAuthn と jose（WebCrypto）が成熟しており、無料枠の CPU とサイズに収まる |
| 共有コア | TypeScript（`packages/core`） | ドメインの規則、入力の検証、SQL 文、ユースケースを 1 か所に置き、Worker と `idpctl` が同じ実装を使う（下の「コードの構成」参照） |
| 管理 CLI / MCP | TypeScript（Node で動く `idpctl`） | 共有コアをそのまま使えるので、D1 を操作するロジックを二重に書かずに済む。MCP 公式 TypeScript SDK で stdio の MCP サーバーを同梱できる |
| パッケージ管理 | pnpm の workspace | コア、Worker、`idpctl` を 1 つのリポジトリで管理し、依存の向きを機械的に確かめられる |
| データベース | D1 | `DELETE … RETURNING` で使い捨て値を原子的に消費でき、無料枠で足りる |
| トークン署名 | RS256（WebCrypto） | OIDC Discovery で RS256 のサポートが必須。 |
| e2e テスト | Playwright（ブラックボックス） | HTTP とブラウザ操作で IdP を外から叩くので実装言語に依存せず、Rust に移行しても同じテストを流せる。仮想オーセンティケータでパスキーの操作を自動化できる |
| ストレージに使わないもの | KV | 結果整合で使い捨て値に向かず、無料枠の書き込みが 1 日 1,000 件と少ない |

`idpctl` は Node で動かし、単一バイナリでの配布は求めない。手元の運用者 1 人が使う道具であり、配布の手間より、Worker と同じコアを使えることを優先する。

**コードの構成**

pnpm の workspace に次の 3 つを置く。

| パッケージ | 中身 | D1 への接続 |
| --- | --- | --- |
| `packages/core` | ドメインの規則（パスキーの上限、最後の 1 本は失効できない規則、無効化されたユーザーの確認など）、入力のスキーマと検証、SQL 文、ユースケース、D1 を操作するポート（インターフェース） | 触れない。ポート越しに、実行する文のバッチを渡すだけ |
| `apps/worker` | D1 バインディングのアダプタと、公開する HTTP（OIDC、パスキー API、静的アセット） | D1 バインディング |
| `apps/idpctl` | D1 REST API のアダプタ、CLI、stdio の MCP サーバー | D1 REST API |

- **規則の実装は 1 つ**：Worker もパスキー（本人による追加と失効、登録リンクによる登録）と監査ログの行を書くので、パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、入力の検証は、Worker と `idpctl` が共有する規則である。これらはコアにだけ実装し、アプリ側に書き直さない。
- **スキーマは 1 つ**：各操作の入力のスキーマはコアで定義し、同じスキーマが入力の検証、CLI の引数、MCP のツールの入力スキーマを決める。
- **アダプタは薄く**：2 つの D1 アダプタは、コアが組み立てた文のバッチを実行して結果を返すだけで、ドメインのロジックを持たない。両方のアダプタが同じ適合テスト（バッチの原子性と途中で失敗したときのロールバック、`DELETE … RETURNING` の結果）を通ることを CI で確かめる。D1 REST API のバッチが途中の失敗で全体をロールバックするかは、まだ確かめていない（[未決事項](open-questions.md)参照）。適合テストが通らない間は、そのアダプタで書き込みを行わない。

**管理系と利用者向けの境界**

設計原則 1（攻撃面を小さくする）を、コードの依存でも守る。

- コアは、利用者向けのユースケース（OIDC、パスキーの登録とサインイン、アカウントページでの本人による操作）と、管理系のユースケース（`idpctl` の操作）を別のモジュールに分ける。両方が使う規則（パスキーの上限、監査ログの行の形、入力の検証など）は、どちらにも属さない共有のモジュールに置く。
- `apps/worker` が import してよいのは、利用者向けと共有のモジュールだけにする。利用者向けのモジュールも管理系のモジュールを import しない。CI の依存の lint でこれを強制し、違反があればビルドを失敗させる。
- CI は、Worker のビルド成果物に管理系のモジュールのコードが含まれていないことも確かめる。lint の設定漏れや間接的な import があっても、成果物の側で止めるため。
- IdP の Worker は、管理操作を HTTP で一切公開しない。管理系のコードがバンドルに入らないので、ルーティングの誤りで管理操作が露出することも起きない。

**今 Rust を採らない理由**

- 実績のある WebAuthn ライブラリ webauthn-rs は OpenSSL 依存で、Workers の Wasm 環境では動かない。
- 純 Rust の `rsa` クレートは Marvin Attack（RUSTSEC-2023-0071）が未修正で、ネット越しに署名を叩ける IdP では使えない。
- 結果として、IdP で最も危険な部分を自前で書くことになる。移行の条件と、移行したときの共有コアの扱いは[Rust 移行計画](rust-migration.md)にまとめる。

**検討して外した候補**

- Gleam：書き味は Rust に近く JS ライブラリも使えるが、FFI の型を自分で保証する必要がある。
- Go（syumai/workers）の Worker：通常の Go はバイナリが大きく無料枠に載らず、TinyGo ではライブラリの互換性が不安。
- Python Workers：無料枠の CPU 10 ms と起動 1 秒の上限に対して重い。
- Go の `idpctl`：単一バイナリで配れ、MCP の公式 SDK も標準の暗号ライブラリもある。しかし、D1 を操作するロジック（パスキーの上限、最後の 1 本の規則、無効化の確認、監査ログの行の形、入力の検証）を Worker の TypeScript と二重に実装することになる。Worker もパスキーと監査ログを書くので、2 つの実装がずれると、同じ規則が書き込みの経路によって変わってしまう。この二重実装のリスクが、単一バイナリの配布の利点より大きいと判断した。
