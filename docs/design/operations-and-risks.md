# 操作とリスク

IdP を通じてできる行為を主体ごとに洗い出し、目的、悪用や誤りのときに誰が影響を受けるか、今の対策を並べる。誰に何を任せるか（AI を含む）は、職種ではなくこの一覧の影響の広さで決める（[認可](authorization.md)、[管理 CLI と管理用の Worker](idpctl.md)参照）。管理の行為は、`idpctl` から管理用の Worker の管理 API を通じて行い、どれも RFC 9421 の署名と署名鍵の許可リストで確定した管理者だけができ、監査ログに管理者の名前と鍵の `keyid` が残る（[ホスティングのモード](hosting-modes.md)の 3）。

**利用者（ブラウザ）**

| 行為 | 目的 | 悪用・誤りの影響 | 今の対策 |
| --- | --- | --- | --- |
| パスキーの登録 | 本人と端末を結び付ける | 登録リンクを他人が使うと、その人として全 RP に入れる | 10 分、1 回だけ、対面で渡す |
| パスキーの追加 | 本人が端末を増やす | 本人の認証器と UV を押さえた攻撃者が、パスキーを足して居座る | 直前の再認証、[パスキーの上限](cross-language-contract.md)、監査ログ（本人への通知はない） |
| パスキーの失効 | 失くした端末のパスキーを止める | 本人の認証器と UV を押さえた攻撃者が、本人の他のパスキーを消して締め出す | 直前の再認証、最後の 1 本は失効できない、監査ログ、管理者による復旧 |
| サインイン | 本人を確認してセッションを作る | セッションを盗まれると、1 時間その人として許可済みの RP に入られる | `__Host-` Cookie、SameSite=Lax、1 時間の絶対期限 |
| サインアウト | 共用の端末で次の人に使わせない | 強制的にサインアウトさせられる（軽微） | 同一オリジンの確認 |
| RP からのログアウト（`/end_session`） | RP でのサインアウトの後に IdP のセッションを残さない | 意図しないログアウト（軽微）。オープンリダイレクト | 今のセッションの hint がなければ確認のページと同一オリジンの確認、登録した `post_logout_redirect_uris` との完全一致 |
| ログアウト後の戻り先の登録（`client_set_post_logout_redirects`） | RP のサインアウトの後に RP へ戻す | 攻撃者のページへの戻り先を登録される | 監査ログ、https だけ、完全一致 |

**RP（OIDC）**

| 行為 | 目的 | 悪用・誤りの影響 | 今の対策 |
| --- | --- | --- | --- |
| 認可の要求 | ユーザーにサインインしてもらう | redirect 先を乗っ取られると、認可コードを盗まれる | redirect URI の完全一致、PKCE |
| トークンの交換 | 本人の情報を受け取る | シークレットが漏れると、その RP を名乗られる | クライアント認証、PKCE、60 秒のコード |
| `/userinfo` | 最新の属性を取る | アクセストークンが漏れると、5 分間読まれる | 毎回アクセス可否を確認し直す |

**ユーザーの管理（idpctl）**

| 行為 | 目的 | 悪用・誤りの影響 | 今の対策 |
| --- | --- | --- | --- |
| ユーザーの作成 | 人を迎える | grant がなければ実害はない | 監査ログ |
| 登録リンクの発行 | 初回の登録、パスキー紛失からの復旧 | 任意のユーザーとして、その人の全 RP に入れる | 10 分、対面、平文はファイルだけ、本人性を確定させる操作として分類する、[パスキーの上限](cross-language-contract.md)に達したユーザーには発行しない |
| パスキーの失効、無効化、セッションの失効 | 事故対応、退去 | 正当な人を締め出す（可用性） | 再登録か `user_enable` で復旧できる。パスキーの失効は最後の 1 本を残す（完全に止めるのは無効化）。ユーザーは削除しない |
| ユーザーの有効化（`user_enable`） | 誤った無効化を戻す、戻ってきた人を迎える | 締め出したはずの人（や、その人のパスキーを持つ攻撃者）を戻す | 監査ログ、今と同じ状態への変更は拒否する |
| 表示名とグループ名の変更 | 事実を正しく保つ | 別人やほかのグループと取り違えさせる | ID は変わらない、変更前後の名前を監査ログに残す |
| グループのメンバーの変更 | 人についての事実を保つ | そのグループに付いた全 RP へのアクセスを間接的に与える | 権限が広がる範囲を表示し、監査ログに残す |
| グループの無効化と有効化（`group_disable`、`group_enable`） | グループ経由のアクセスをまとめて止める、戻す | 無効化はメンバー全員を締め出し、有効化はメンバー全員にグループの grant をまとめて戻す | 監査ログ、所属と grant は残るので戻せる、グループは削除しない |

**RP とアクセスの管理（idpctl）**

| 行為 | 目的 | 悪用・誤りの影響 | 今の対策 |
| --- | --- | --- | --- |
| RP の登録 | 新しいアプリをつなぐ | grant がなければほぼない（パスキーは IdP の origin に縛られる） | 監査ログ |
| redirect URI の変更 | 移転、環境の追加 | その RP の利用者全員の認可コードを盗める | 監査ログ |
| シークレットの更新 | 漏洩への対応 | 新しいシークレットで、その RP を名乗れる | 平文はファイルだけ |
| ID トークンの署名アルゴリズムの変更（`client_set_id_token_alg`） | Ed25519 を検証できない RP に RS256 を使わせる、戻す | その RP が ID トークンを検証できなくなり、サインインできなくなる | 監査ログ、RS256 が無効な間は `RS256` の登録を拒否する |
| RP の無効化と有効化（`client_disable`、`client_enable`） | 使わなくなったアプリを止める、戻す | 無効化はその RP の利用者全員を締め出し、有効化は残っている grant と redirect URI をそのまま戻す | 監査ログ、client は削除しないので ID が再利用されない、無効な client の `/authorize` はリダイレクトしない |
| grant | RP を使える人を決める | 主体（グループなら全メンバー）に、その RP を過剰に使わせる | 権限が広がる範囲を表示し、監査ログに残す |

**基盤（運用者）**

| 行為 | 目的 | 悪用・誤りの影響 | 今の対策 |
| --- | --- | --- | --- |
| 署名鍵の生成と登録 | トークンに署名する | 全ユーザーの全 RP 向けトークンを偽造できる | レビュー済みの生成スクリプトだけで生成する、平文をディスクにも AI のコンテキストにも出さない、1Password |
| D1 の API トークン | break-glass（管理用の Worker が使えないとき） | 上の管理の区分をすべて迂回でき、共有コアの規則も監査ログも通らない。トリガーを外せば行も消せる | 日常は使わない、前もって作らず、必要なときだけ短い有効期限で作って終わったら失効させる。D1 の権限はアカウント単位なので、IdP をサービスのアカウントに置くと、サービスの D1 の権限を持つトークンも同じ影響を持つ（[ドメインの置き場所](domain-placement.md)の共存の設計の 6） |
| 管理者の鍵の生成 | 管理者に署名鍵を持たせる | 秘密鍵が漏れると、許可リストから消すまでその管理者として何でもできる | レビュー済みの生成スクリプトだけで生成する、平文をディスクにも AI のコンテキストにも出さない、1Password。鍵だけでは管理 API に入れない（許可リストが要る） |
| 許可リストの変更 | 管理者を足す、外す、鍵を替える | 任意の公開鍵を管理者にできる | 管理用の Worker の設定（`admin_signing_keys`）としてリポジトリに置き、CI のデプロイでだけ変える。D1 にも管理 API にも置かない |
| Worker のデプロイと Terraform の apply | コード、設定（許可リストを含む）、基盤（DNS）を更新する | コードの差し替えで何でもできる。リダイレクト、TLS のバージョン、署名の検証、レート制限もすべて Worker のコードにある | CI（GitHub OIDC、1Password Environments）。main へのマージで手動の承認なしに走るので、main のブランチのルールセット（PR のレビューとマージの権限）が唯一の関門になる |
| `workers.dev` のサブドメインと Worker の名前の変更（`workers.dev` のモード） | アカウントの設定、コードの整理 | issuer が変わり、全員のパスキーが使えなくなり、RP からは別の IdP に見える。手放したサブドメインを別のアカウントが取れれば、古い issuer をなりすまされうる（未確認） | 変えない前提で運用する。Worker の名前はコードの定数で、変える PR は issuer の変更として扱う。デプロイのスクリプトが実際のサブドメインを入力と照らし合わせて、違えば止まる（[ホスティングのモード](hosting-modes.md)の 2.3） |
| サービスのアカウントの Workers と D1 の権限（IdP をサービスのアカウントに置くとき） | サービスの運用 | IdP の Worker の差し替えと D1 の読み書きで、IdP の全利用者の全 RP に入れる。Workers と D1 の権限はアカウント単位で、IdP に絞れない | サービスの運用者が IdP の管理者と同じであることを、この形を選ぶ条件にする。違えば IdP 専用のアカウントを持つ形にする（[ドメインの置き場所](domain-placement.md)） |
| ゾーンの設定とルールの変更（ゾーンの持ち主。IdP をサービスのゾーンに置くとき） | サービスのホスト名を守る、設定を変える | IdP はゾーンのルールセットを持たず頼らないので、ゾーンのルールの変更で IdP の保護は外れない。ゾーンの TLS の最小バージョンを 1.2 より下げると、TLS 1.0 と 1.1 の接続が成立する（Worker は要求を処理しない。RFC 8996 の例外）。IdP は managed CA の割り当てを持たない（mTLS は[ホスティングのモード](hosting-modes.md)の実装の順番の 7 で外した）ので、ゾーンの持ち主が managed CA を使っても取り合わない | ブートストラップの前提で、TLS の最小バージョンをゾーンの持ち主に確かめる（[ドメインの置き場所](domain-placement.md)の決定 ③ と共存の設計の 2、3） |

**認証のない外部の要求**

IdP はゾーンのルールで要求を止めない（[ドメインの置き場所](domain-placement.md)の決定 ③。`workers.dev` のモードにはゾーンがない）ので、次の要求はすべて Worker に届き、拒否されても Workers の 1 日のリクエスト上限（アカウント全体で 10 万件）に数えられる。

| 行為 | 目的 | 悪用・誤りの影響 | 今の対策 |
| --- | --- | --- | --- |
| 管理用のホスト名への、署名のない（または許可リストにない鍵の、正しくない署名の、リプレイの）要求 | 攻撃、探索 | 管理 API には入れない。管理用の Worker に届き、1 日のリクエスト上限を使う。正しい形の要求で署名の検証の CPU 時間を使わせられる。大量に送ると、上限を共有するアカウント全体（IdP の Worker、サービスの Worker）が UTC 0 時まで止まる | 管理用の Worker の Rate Limiting バインディングが IP ごとに CPU 時間を守り、ゲートが D1 にも IdP の Worker にも触れる前に `forbidden` で拒否する（`nonce` の行も書かない）。上限の消費は防げず、受け入れる（[無料枠](free-tier.md)） |
| IdP のホスト名への大量の要求（ページを含む） | 攻撃 | 同じく 1 日のリクエスト上限を使い切れる。認証前の D1 の書き込みも使う | IdP の Worker の Rate Limiting バインディングが、IP ごとに D1 の書き込みと CPU 時間を守る。上限の消費は防げず、受け入れる（[無料枠](free-tier.md)） |
| 平文の HTTP の要求 | 古いリンク、誤った設定 | 資格情報を平文で送った時点で露出している | IdP の Worker は、IdP の資格情報（`Authorization`、`__Host-` の名前の Cookie）のない `GET` と `HEAD` だけを HTTPS へ 308 でリダイレクトし、ほかは処理せず拒否する。サービスの親のドメインの Cookie はリダイレクトを妨げない。管理用の Worker は拒否だけ |

**影響の広さ**

- 全ユーザー × 全 RP：署名鍵、D1 の API トークン、デプロイと Terraform の apply（許可リストの変更を含む）、main へのマージの権限。IdP をサービスのアカウントに置くときは、そのアカウントの Workers と D1 の権限も。管理者になるには、許可リストの変更（デプロイの権限）が要る。管理者の秘密鍵を盗まれると、許可リストから消すまでその管理者の全操作ができる。`workers.dev` のモードでは、アカウントの `workers.dev` のサブドメインの変更も、issuer を変えるので全ユーザー × 全 RP に効く。
- 1 人のユーザー × その人の全 RP：登録リンク。ユーザー 1 人分とはいえ、基盤に近い強さを持つ。メールアドレスを持たない（[トークン設計](tokens.md)参照）ので、`email_verified` による同じ段階の経路はない。
- 1 つの RP × その全利用者：redirect URI、シークレット、RP の無効化と有効化。
- 主体 × RP：グループのメンバーの変更、グループの無効化と有効化、grant。グループのメンバーの変更は、グループに付いた grant を通じて効く間接的な付与になる。
