# ブートストラップ

空の Cloudflare アカウントから、IdP を動かし、最初のユーザーと RP をつなぐまでの手順の設計。手順の中身（Terraform とスクリプト）は実装の作業で、このドキュメントは順番と、各段階で確かめることだけを決める。秘密の値を埋め込んだコマンドは書かない。

最初は検証用のアカウントにこの手順を通し、本番は IdP のホスト名を持つゾーンのアカウント（典型的には IdP が仕えるサービスのアカウント。[ドメインの置き場所](../design/domain-placement.md)）に、同じ手順をもう一度通して作る。手順はアカウントに依存せず、変わるのは[デプロイと設定](../design/deployment.md)の「デプロイごとの入力」だけにする。アカウント ID、ゾーン ID、D1 の ID、ホスト名を、手順にもスクリプトにも書かない。

手順は 2 つのホスティングのモード（カスタムドメインと `workers.dev`。[ホスティングのモード](../design/hosting-modes.md)）で同じで、違うのはゾーンに関わる前提と確認だけ。管理者の認証は、どちらのモードでも RFC 9421 の署名で行う。

移行の間の注意：この文書は、管理者の認証を署名だけにした後の手順を書く。管理用の Worker は[ホスティングのモード](../design/hosting-modes.md)の実装の順番の 6 で署名だけで管理者を確かめるようになったので、段階 6 の管理者の確認は署名で行う。mTLS の撤去（実装の順番の 7）までは、Terraform がまだ mTLS の割り当てとクライアント証明書を持つので、段階 4 は[実行手順](runbook.md)の「移行の間の手順」に従う。`workers.dev` のモードの入力は、同じ文書の実装の順番の 8 で足すまで使えない。

## `workers.dev` のモードを選ぶ前の警告

`workers.dev` のモードを選ぶ人は、最初に次を読む（[ホスティングのモード](../design/hosting-modes.md)の 2.4）。

- issuer と RP ID は、アカウントの `workers.dev` のサブドメインと IdP の Worker の名前で決まる。後からカスタムドメインに移ると、全員のパスキーの登録し直しと、すべての RP の設定の移行が要る。長く使うつもりなら、最初からカスタムドメインのモードを選ぶ。
- アカウントの `workers.dev` のサブドメインを変えない。Worker の名前を変えない。どちらも issuer を変える。手放したサブドメインは、別のアカウントに取られるかもしれない（未確認）。
- Cloudflare は、本番の Worker を `workers.dev` ではなくルートかカスタムドメインで動かすことを勧めており、`workers.dev` を業務上重要でない個人や趣味のプロジェクト向けとしている。
- `workers.dev` へのすべての要求は Browser Integrity Check を受け、無効にできない。ライブラリの既定の `User-Agent` を送る RP のサーバーは、Worker に届く前に Error 1010 で拒否されうるので、つなぐ RP ごとに確かめる。
- 同じアカウントのほかの Worker は、IdP と same-site になる。IdP の確認で止まるが、アカウントにほかの Worker を置くなら、その Worker の権限を持つ人が IdP の Worker も差し替えられる。

## 前提

- 次は、手順の前に運用者がダッシュボードで行う。API やスクリプトにできないか、認証情報を作る操作で、エージェントには任せない（[AGENT.md](../../AGENT.md) 参照）。デプロイと設定の「手作業の手順を残さない」の例外として、ここに列挙して管理する。
  - カスタムドメインのモード：ゾーンの追加と、ネームサーバーの切り替え（ゾーンがまだないとき。サービスのゾーンを使うときは要らない）
  - カスタムドメインのモードで、ゾーンをサービスと共有するときの、ゾーンの持ち主との確認。IdP はゾーンのルールセットも設定も持たない（[ドメインの置き場所](../design/domain-placement.md)の決定 ③）ので、ルールの合意は要らない。確かめるのは、ゾーンの TLS の最小バージョンが 1.2 以上であること（同じ文書の共存の設計の 3）
  - `workers.dev` のモード：アカウントの `workers.dev` のサブドメインの作成（まだないとき）。上の警告を読んだうえで、変えないサブドメインを選ぶ
  - IdP の Worker と管理用の Worker の、Rate Limiting の名前空間の ID の選択（2 つ）。アカウントの中で一意なので、互いに違い、サービスの Worker が使っていない値にする
  - R2 の有効化（無料枠の範囲でも、支払い方法の登録と R2 の利用の手続きが要る）
  - 役割ごとの API トークン（[デプロイと設定](../design/deployment.md)の API トークン）と、state のバケットの R2 の S3 互換の認証情報の作成。どれもアカウント単位なので、アカウントごとに作る
  - 1Password の Environment と GitHub Actions の destination の作成（[1Password Environments と GitHub Actions](secret.md)参照）
- 鍵と秘密は、すべてリポジトリのレビュー済みの生成スクリプトで生成する。手で生成しない（[デプロイと設定](../design/deployment.md)の鍵と秘密の生成スクリプトを参照）。
- 宣言できる基盤は Terraform、手続きの操作は `cf` のシェルスクリプトで行う（[デプロイと設定](../design/deployment.md)の Terraform とスクリプトの分担を参照）。
- D1 には初期データを入れない。管理者の認証は IdP のユーザーから独立している（署名と署名鍵の許可リスト）ので、空のデータベースから始められる。
- 管理者の名前（許可リストの名前）は、どの `users.id` にも結び付けない。管理者であることと、IdP の利用者であることは別の事実で、片方の欠陥がもう片方に広がらないようにするため（[将来拡張](../design/future-extensions.md)の管理権限の分離を参照）。
- 許可リストが空なら、管理用の Worker はすべての管理リクエストを拒否する（fail-closed）。そのため、手順の順番を間違えても、管理 API が開いたままになることはない。

## 実行する場所と認証情報

- 段階 1〜4 は、最初の CI のデプロイより前なので、運用者の手元で実行する。実行するのは運用者か、運用者がすでに認証した `cf` と `op` のセッションの下のエージェントで、どちらでもリポジトリの同じスクリプトと Terraform の設定を使う（[AGENT.md](../../AGENT.md) 参照）。
- `cf` のスクリプトは、運用者が `cf auth login` で認証したセッションを使う。このセッションは複数のアカウントにまたがりうるので、スクリプトは `cf` を呼ぶたびに入力のアカウント ID を明示し、変更の前に対象のアカウントを確かめる（[デプロイと設定](../design/deployment.md)の直書きの禁止を参照）。
- スクリプトと Terraform は、デプロイの設定ファイル（`deployments/<デプロイの名前>.tfvars.json`）と、1Password から受け取るアカウント ID だけを入力にする。入力が欠けていれば、何もせずに止まる。
- 手元の Terraform は、Terraform 用の API トークンと state の R2 の認証情報を、1Password の Vault のアイテムから `op` で実行時にプロセスの環境変数として受け取る。値をファイルやコマンドラインに書かない。CI 用の 1Password Environment とは別に、人が使う認証情報として Vault に置く（[1Password Environments と GitHub Actions](secret.md)の Vault と Environment の境界を参照）。
- 段階 5 以降の Terraform の apply、マイグレーション、デプロイは、すべて CI で行い、手元からは行わない。

## 手順

| 段階 | 行うこと | 場所と道具 | 確かめること |
| --- | --- | --- | --- |
| 0 | ホスティングのモードを決め、デプロイごとの入力を決める。アカウント ID を 1Password に置き、それ以外の入力（`hosting_mode`、カスタムドメインのモードでは issuer と管理用のホスト名、`workers.dev` のモードではアカウントのサブドメイン、2 つの Rate Limiting の名前空間の ID を含む）をデプロイの設定ファイルに書く。許可リストは空にしておく | 手元。1Password、リポジトリの設定ファイル（PR でレビューする） | 入力の一覧（[デプロイと設定](../design/deployment.md)のデプロイごとの入力）がモードで必須のものだけそろい、禁止のものがなく、アカウント ID がリポジトリにないこと。issuer は運用を始めた後に変えない（[デプロイと設定](../design/deployment.md)のホスト名を変えるときの影響を参照） |
| 1 | Terraform の state 用の R2 のバケットを作る。D1 のデータベースを APAC で作る | 手元。`cf` のスクリプト（バケットと D1。Terraform には D1 を置かない。[デプロイと設定](../design/deployment.md)の Terraform とスクリプトの分担を参照） | バケットと D1 が入力のアカウントにあること。D1 の ID はスクリプトが名前から引き、設定ファイルにも手順にも書き写さないこと。D1 が production バックエンドにあること（Cloudflare API の「Get D1 Database」の `version`。[未決事項](../design/open-questions.md)参照） |
| 2 | マイグレーション（テーブル、ビュー、トリガー）を適用する | 手元。`cf` のスクリプト | トリガーが更新と削除を拒否すること（[データモデル](../design/data-model.md)参照） |
| 3 | トークンの署名鍵（Ed25519）を生成し、1Password のアイテムにだけ入れる。Worker Secret には、まだ登録しない（Worker がまだないため。段階 5b で登録する） | 手元。生成スクリプト | 出力が `kid` と公開鍵だけで、平文がディスクにないこと |
| 4 | 管理者の鍵（ECDSA P-384）を生成し、公開鍵と `keyid` の行をデプロイの設定ファイルの許可リスト（`admin_signing_keys`）に足す。CSR もクライアント証明書も作らない。Terraform を適用する（ゾーンのルール、mTLS の割り当て、証明書は置かない。Worker のカスタムドメインは段階 5 の `cf deploy` が付けるので、Worker がないうちに適用してよい） | 手元。生成スクリプト（鍵と許可リストの行）、Terraform、リポジトリの設定（許可リスト。PR でレビューする） | 秘密鍵が 1Password にだけあり、出力が公開鍵と `keyid` だけであること。許可リストの `keyid` が 1Password のアイテムの `public_key_sha256` と一致すること。plan がゾーンのルールセットと設定を変えないこと |
| 5 | 2 つの Worker を CI で最初にデプロイする | CI（[デプロイと設定](../design/deployment.md)のデプロイのパイプライン） | main へのマージから、apply、マイグレーション、2 つのデプロイが順に成功すること。IdP の Worker は署名鍵がないので、リクエストを処理せずエラーを返すこと（fail-closed） |
| 5b | 段階 3 の署名鍵を、IdP の Worker の Worker Secret に登録する | 手元。Secret の登録スクリプト（1Password から読み、`cf` か Cloudflare API へパイプで渡す） | 出力が `kid` だけで、IdP の Worker の新しいバージョンが鍵を読めること |
| 6 | 動作を確かめる | — | discovery と JWKS に届き、JWKS の `kid` が段階 3 の `kid` と一致すること。署名のない管理 API の要求と、許可リストにない鍵の署名の要求に管理用の Worker が `forbidden` を返し、許可リストの鍵で署名した `idpctl` の要求が通ること。同じ署名の要求を送り直すと `forbidden` になること（リプレイ）。拒否した要求の後に `admin_request_nonces` と監査ログの行が増えていないこと、通った要求の監査ログの行が管理者の名前、`keyid`、`admin_credential` の `signing-key` を持つこと。同じ接続元から 10 秒に 10 件を超える管理 API の要求が、本文のない 429 になること。管理用のホスト名への平文の要求がリダイレクトされず拒否されること。`workers.dev` のモードでは、`idpctl` の要求と、つなぐ RP のサーバーの discovery、JWKS、`/token` の要求が Browser Integrity Check で拒否されないこと（`User-Agent`）。issuer への平文の `GET`（ページ、例えば `/signin`）が同じパスとクエリの HTTPS に 308 でリダイレクトされ、平文の `POST /token` が 404 で拒否されること（ゾーンの Always Use HTTPS が有効なら、エッジのリダイレクトが先に返る）。TLS 1.1 以下で届いた要求を、ページを含めて 2 つの Worker が拒否すること（ゾーンの最小バージョンが 1.2 以上ならハンドシェイクで失敗する）。カスタムドメインのモードでは、サービスのほかのホスト名の動きが変わっていないこと |
| 7 | `idpctl` で、自分のユーザー、登録リンク、自分のパスキー、グループ、最初の RP、grant を作る | 手元。`idpctl` | `access_check` で、自分がその RP を使えること |

- 段階 4 の許可リストの変更は、段階 5 のデプロイで初めて効く。段階 5 より前に管理 API を呼んでも、空の許可リストですべて拒否される。
- 署名鍵の登録を最初のデプロイの後（段階 5b）に置くのは、Worker Secret が Worker に属する値で、Worker がないうちは登録先がないため。署名鍵を CI の 1Password Environment に置いてデプロイと一緒に上げる形は取らない。デプロイ用の認証情報に署名鍵まで持たせると、CI が漏れたときの影響が全ユーザーのトークンの偽造にまで広がるため。
- 段階 5b の登録の方法は、`cf` が平文をディスクに書かずに Secret を登録できるかで決まる（`cf deploy --secrets-file` か `cf workers versions create --secrets-file` が標準入力やパイプを受け付けるか。[未決事項](../design/open-questions.md)参照）。受け付けなければ、Cloudflare API で登録する。どちらの方法でも、登録すると IdP の Worker の新しいバージョンができる。今の登録スクリプトは、`cf workers secrets update` に要求の本文を標準入力から渡す形で実装した。受け付けられるかは最初の実行で確かめる（[実行手順](runbook.md)の未確認のこと）。
- 各段階で運用者が実行するスクリプトと順番は[実行手順](runbook.md)にまとめる。
- 段階 3 と 4 の生成スクリプトと、段階 5b の登録スクリプトは秘密を扱うので、`-x` を付けない（[デプロイと設定](../design/deployment.md)のシェルスクリプトの規則を参照）。
- 段階 7 の登録リンクの平文は `idpctl` が `0600` のファイルに書き、パスだけを表示する（[管理 CLI と管理用の Worker](../design/idpctl.md)参照）。

## 失敗したとき

- 段階 1〜4 は、やり直しても結果が同じになるように作る（Terraform は宣言なので同じ状態に収束し、生成スクリプトは新しい鍵を作って古いものを置き換える）。段階 1 の D1 の作成スクリプトは、同じ名前のデータベースがあれば作らずに止まり、既存のデータベースを置き換えない。
- 段階 3 か 4 の後に鍵が漏れた疑いがあれば、同じ生成スクリプトで作り直し、1Password と Worker Secret を置き換える。管理者の鍵は、古い行を許可リストから外してデプロイする。
- 段階 5 のデプロイが途中で止まったら、パイプラインは最初の失敗で止まるので、原因を直して main にもう一度マージする。

## 別のアカウントに作り直すとき

- 新しいアカウントの入力で、段階 0 から同じ手順を通す。手順、スクリプト、Terraform のコードは変えない。変える必要が出たら、それは移植性の欠陥なので、先に[デプロイと設定](../design/deployment.md)を直す。
- D1、署名鍵、管理者の鍵は新しく作る。古いアカウントからデータを移さない。issuer が変わるので、利用者はパスキーを登録し直し、RP は新しい issuer に設定し直す（[デプロイと設定](../design/deployment.md)のアカウントの移植性を参照）。
- 本番の前に、この手順で 2 つ目のアカウントへのブートストラップが最後まで通ることを確かめる（[未決事項](../design/open-questions.md)参照）。
